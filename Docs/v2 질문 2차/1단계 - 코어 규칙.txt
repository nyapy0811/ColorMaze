    - 각 1~5
    - 각 1~10
    - 스테이지/맵별로 다르게 설정

  - 0 허용 (R/G/B 각 0~N)

  - 일부만 허용 (예: 목표 오브는 각 1~N, 소지 오브는 0 가능)

이유: 0 허용 여부가 목표 오브의 다양성, 합성 가능성, UI 표현(색 표시), 온보딩 난이도와 퍼즐 설계 공간에 영향을 준다.

Q110. [핵심] 구역 리셋과 '재획득 불가' 규칙의 충돌 처리
(통합 질문: Q110 + Q364)

체크포인트 복귀로 구역의 오브젝트를 리셋할 때, 이미 추출했던 오브는 다시 추출할 수 있는가? 아니면 그 구역에서는 맵 초기화 전까지 영구히 재획득 불가인가? 체크포인트 이후 구간의 오브젝트에도 같은 규칙이 적용되는가?

  - 체크포인트는 그 이후 구간의 오브젝트만 리셋 (이전 구간은 유지)
  - 체크포인트 복귀 시 해당 구역 오브젝트를 모두 리셋하여 재추출 가능
  - 체크포인트와 무관하게 한 번 추출한 오브젝트는 맵 초기화 전까지 영구 재획득 불가
  - 체크포인트마다 오브젝트 상태를 독립적으로 관리 (중복 획득 가능)

참고 코드: v2 결정 로그 3절 Q20, v1 MapDesignRules 6절

답: 체크포인트에 도달하면 그 순간의 맵과 플레이어 상태를 저장, 체크포인트 복귀하면 저장 상태로 회귀. 맵 재시작은 첫 시작지점으로 가는것이라 체크포인트 상관없이 맵 초기화

Q116. [핵심] 합성 입력 시 오브의 소모 방식

합성기에 오브 N개를 입력했을 때, 합성 완료 후 입력한 오브를 전부 소모할 것인가, 아니면 일부만 소모하고 나머지는 반환할 것인가?

  - 전부 소모 (항상 입력한 오브를 모두 사용)
  - 일부만 소모 (합성 성공하면 필요한 만큼만, 초과분은 반환)
  - 선택 입력 (플레이어가 각 오브 개수를 조절 후 합성)

이유: 전부 소모면 단순하지만 낭비 가능성이 있고, 일부만 소모면 복잡하지만 유연성이 있다. v1 StackModifierConsumable의 '바뀐 게 있으면 소모' 방식과 유사한지 다른지 명확히 해야 한다.

답: 합성기에서 합성할 오브를 직접 선택, 합성 시행시 선택된 오브들 전부 제거후 결과오브 획득

Q117. [핵심] 합성 UI의 입력 방식과 결과 미리보기·확인 단계
(통합 질문: Q117 + Q123 + Q130 + Q205)

합성기 UI에서 (1) 여러 오브를 고를 때 선택 순서가 결과에 영향을 주는가, (2) 한 번 고른 오브를 해제/재정렬할 수 있는가, (3) 합성 결과를 미리 보여주는가(실시간 계산인지, 실행 후인지), (4) 최종 확인 단계(확인 버튼)가 있는가?

  [입력/확정 흐름]
    - 선택 즉시 합성 (미리보기·해제·확인 없음, 되돌리기 없음)
    - 선택 후 결과 미리보기만 (확인 없이 바로 합성)
    - 선택(해제 가능) → 결과 미리보기 → 확인 버튼
    - 슬롯 선택 → 미리보기 → 확인의 3단계
  [선택 순서]
    - 순서 무관 (가산 교환성)
    - 순서 유관 (조합, 재정렬 가능)
  [미리보기 표시]
    - 실시간 계산해 결과색 표시
    - 합성 실행을 누른 뒤에만 결과 표시
    - 성공/실패만 표시
    - 선택한 오브 수만 표시

이유: UI 상태 관리와 구현 복잡도, 플레이어의 실수로 인한 소프트락(재시작) 빈도가 크게 달라진다. 1차 Q12에서 합성 실패 시 재시작이 의도로 정해졌다.

답: 슬롯 선택하면 실시간으로 출력 오브 보여줌 -> 출력 오브 클릭시 합성 시행, 순서 무관, 미리보기 실시간

Q118. [핵심] 한도를 넘는 조합의 UI 처리
(통합 질문: Q118 + Q219)

플레이어가 합성기에서 한도를 넘는 조합(예: 합이 채널 한도 초과)을 만들려 할 때, 어느 시점에 어떻게 막을 것인가? 한도 초과 오브 자체를 거절할지도 포함해서 답해 주세요.

  - 선택 UI에서 한도 초과 조합을 선택할 수 없게 (버튼 비활성화)
  - 선택 후 실행 전에 경고, 취소/진행 선택
  - 합성 시도 시 실패 처리 (페널티 포함 가능)
  - 초과 오브를 자동으로 제거
  - 한도 초과 오브 자체를 거절

이유: 선택 단계에서 막으면 실수가 없지만 UI가 복잡해지고, 실행 전에 막으면 단순하지만 혼란이 생길 수 있다. 피드백 방식에 따라 플레이어 혼란도와 진행 흐름이 달라진다.

Q119. [핵심] 합성기의 상태 유지 여부

합성기가 입력받은 오브들을 임시 저장하는 내부 상태를 가지는가(상태 보관 합성기), 아니면 상태 없는 순수 UI 장치인가(UI 합성기)?

  - 상태 없음 (UI만, 합성은 클릭 후 즉시 출력 슬롯에 들어감)
  - 상태 보관 (입력 슬롯이 있어 오브를 모았다가 합성)
  - 상태 임시 (UI 호출 중에만 입력 버퍼, 닫으면 초기화)

이유: 상태 보관이면 합성기 사이에서 오브를 옮길 수 있지만 구현이 복잡하고, 순수 UI면 단순하지만 기능이 제한된다. v1의 팔레트/버킷은 상태가 없다.

Q120. [핵심] 슬롯이 가득 찬 상태에서의 합성 결과 처리
(통합 질문: Q120 + Q126)

합성이 완료되었는데 슬롯이 가득 찬 경우, 결과 오브는 어떻게 되는가?

  - 합성 자체를 불가능하게 하고 미리 경고
  - 결과를 버림 (플레이어가 슬롯을 미리 비워야 함)
  - 바닥에 떨어져 나중에 줍기
  - 임시 공간에 대기
  - 플레이어가 자리를 만들 때까지 대기
  - 자동 내려놓기

이유: 슬롯 관리 로직, 합성 UX, 게임 진행 불가(소프트락) 가능성에 영향을 준다.

답: 합성시에 재료 오브가 사라지고 출력오브를 획득하므로 슬롯이 가득찰 가능성은 없음

올바른 오브를 제출했을 때 (1) 어떤 연출(문 열림 애니메이션, 파티클, 효과음, 카메라 효과)을 줄 것인가, (2) 연출 구조는 '즉시 확정'인가 '입력→연출→확정'(취소 가능 여부 포함)인가, (3) 이 연출의 디테일을 지금 정의할 것인가, 프로토타입 후 조정할 것인가?

  [연출 요소]
    - 사운드만 (성공 효과음)
    - 파티클/색상 이펙트만
    - 사운드 + 파티클 (성공/실패 구분)
    - 문이 슬라이드/회전하며 열리는 애니메이션 포함
    - 카메라 쉐이크 포함
  [연출 구조]
    - 즉시 제출, 별도 연출 단계 없음
    - 제출 입력 → 연출 → 자동 확정
    - 제출 입력 → 연출 → 확인/취소 선택
  [정의 시점]
    - 지금 자세히 정의
    - 프로토타입 후 실제 플레이로 조정 (지금은 대략적인 방향만)
    - 개발자(사용자) 재량에 맡김

이유: 연출은 게임의 만족도와 피드백 명확성을 좌우하고, 구조가 복잡할수록 UI 상태 관리와 취소 로직이 복잡해진다. 오디오/파티클 에셋 제작 계획에도 필요하다. (성공 효과음 유무 질문 포함)

Q146. [핵심] 목적지와 문의 기능 분리

v2에서 문(문, 레이저 벽)과 목적지가 모두 오브를 제출받습니다. 목적지는 제출 오브를 소비(사라짐)하고 클리어 조건으로 동작하고, 문은 제출 오브를 보관했다가 나중에 제출 오브를 반환하거나 계속 보유해야 합니다. 문에 남은 오브의 회수 방식은?

  - 문에 남은 오브는 영구 보유(회수 불가), 같은 문에 오브를 다시 제출할 수 없음
  - 문을 다시 조준해 좌클릭하면 제출한 오브를 회수 가능
  - 문이 닫힐 때 자동으로 제출한 오브를 분사/반환해 플레이어가 회수

이유: 오브 회수 불가면 오브 슬롯 관리가, 회수 가능하면 제출/회수 UI 및 인터랙션 복잡도가 달라집니다.

Q149. [핵심] 문에 제출한 오브의 회수 가능 여부
(통합 질문: Q149 + Q151 + Q152 + Q165)

문에 제출한 오브를 나중에 회수해서 다른 문에 쓸 수 있는가? (참고: 1차 Q22는 '제출한 오브는 문에 남는다'까지만 정했고, 회수 기능은 정해진 바 없습니다. 아래 질문은 회수 도입 여부를 묻는 것입니다.) 회수 가능하다면 (1) 어떻게 회수하는가(문을 조준+클릭, 별도 UI, 자동 반환), (2) 슬롯이 가득 찬 상태에서는 어떻게 되는가, (3) 문 A에서 회수해 문 B에 쓰는 중복 사용을 허용하는가?

  [회수 여부]
    - 회수 불가 (제출한 오브는 문에 영구히 남음)
    - 회수 가능 (회수 UI 제공)
    - 조건부 회수 (특정 기물만 또는 특정 조건에서만)
  [회수 방법 (가능한 경우)]
    - 문을 다시 조준+클릭
    - 별도 UI에서 관리
    - 문이 비활성화될 때 자동 반환
  [슬롯이 가득 찼을 때 (가능한 경우)]
    - 회수 불가, 문이 오브를 계속 보유
    - 회수 실패 표시/효과 재생
    - 슬롯과 관계없이 자동 반환

이유: 문 시스템에서 오브 재사용 가능성이 퍼즐 설계에 직결된다. 회수가 가능하면 슬롯 부족 시 반환 처리 같은 복잡한 로직이 필요하고, 불가능하면 문마다 별도의 오브가 필요해 오브 수급 설계가 달라진다.
