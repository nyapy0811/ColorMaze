Q101. [핵심] 오브 값의 코드 데이터 형식

무엇을 정하는 질문인가: 오브의 R/G/B 값을 코드와 save.json에서 어떤 타입으로 다룰지입니다. 합성(덧셈), 제출 판정(완전 일치), 저장, 맵 제작 때의 값 입력이 모두 이 타입을 거칩니다.

[이미 정해진 전제]
  - 채널 값은 0~N, N은 맵별 설정(기본 5), 0 허용. (Q102, Q103)
  - 같은 값이어도 별개의 오브이고 슬롯 1칸씩 차지합니다. 오브를 제출하면 그 칸은 빈칸으로 남습니다. (Q104, Q142)
  - 합성은 채널별 덧셈이고, 한도(N)를 넘는 선택은 자동으로 해제됩니다. (Q117, Q118)
  - 슬롯의 오브는 체크포인트 스냅샷과 save.json에 저장됩니다. (Q105, Q110)
  - 1차 Q11에서 나중에 "음수 값을 가진 합성용 오브(감산)"를 추가할 수 있다고 했습니다.

[코드에서 확인한 사실]
  - save.json은 Framework.Core의 SaveManager가 Unity JsonUtility로 저장합니다. SaveData에는 "List는 지원, Dictionary는 안 됨"이라는 주석이 있습니다. JsonUtility는 [Serializable] 구조체/클래스와 List<T>는 저장하지만 Dictionary, 중첩 컬렉션(배열의 배열 등)은 저장하지 못합니다.
  - v1 ColorStacks는 readonly int[] values = new int[3]로 R/G/B를 들고 있고, 표시용 색은 ToRGB/CurrentRGB (채널 = 255 × 값 ÷ StackMax)로 따로 변환합니다.
  - v1 이벤트(ColorStackChanged)는 struct입니다. 맵 기물 요구 값은 ColorCanvas의 targetRed/Green/Blue 정수 필드 3개였습니다.

[선택지]

[A. int[3] 배열 (v1 ColorStacks 방식)]
  - 장점: v1과 같아서 익숙합니다. 음수도 담을 수 있습니다.
  - 단점: 값 비교가 참조 비교라서 매번 세 칸을 직접 비교하는 코드를 써야 하고 실수하기 쉽습니다. + 연산을 쓸 수 없고 Dictionary/HashSet 키로도 못 씁니다. 슬롯 목록이 List<int[]>가 되는데 JsonUtility가 중첩 컬렉션을 저장하지 못해 결국 감싸는 클래스가 필요합니다. [0]=R, [1]=G, [2]=B라는 암묵적 약속에 의존하고 길이 3을 강제할 수 없습니다.

[B. 튜플 (int r, int g, int b)]
  - 장점: 필드 이름이 있고 == 비교가 기본 지원되며 가볍습니다.
  - 단점: Unity 직렬화가 정식 지원하는 형식이 아닙니다(저장되더라도 필드 이름이 Item1·Item2·Item3). 인스펙터에 나오지 않아 맵 제작 때 목표 값 입력에 쓸 수 없습니다. 저장용 변환 타입을 따로 만들게 되어 결국 D가 추가로 필요합니다.

[C. Color32]
  - 장점: Unity 표준 타입이고 직렬화와 인스펙터 편집이 됩니다.
  - 단점: 채널이 byte(0~255)이고 알파 채널이 붙어 있어 오브(0~N, 알파 없음)와 의미가 맞지 않습니다. 음수를 담을 수 없어서 나중에 음수 오브를 넣으려면 타입을 다시 바꿔야 합니다. 맵마다 N이 달라서 값 ↔ 색 변환을 항상 신경 써야 하고, "표시용 색"과 "규칙용 값"이 섞이면 버그가 납니다. (표시용 색 변환은 어떤 선택지를 골라도 별도 함수로 둡니다.)

[D. 전용 구조체 OrbValue { int r, g, b } ([Serializable] struct)]
  - 장점: 이름이 의도를 드러냅니다. JsonUtility로 저장되고 인스펙터에서 편집됩니다(맵 제작 때 목표 값 입력에 그대로 사용). operator +와 ==, Equals, GetHashCode를 직접 구현해 합성(덧셈)과 판정(일치)이 한 줄로 끝납니다. Dictionary/HashSet 키로 쓸 수 있습니다. int라서 음수 확장이 가능합니다. 값 타입이라 복사와 비교가 안전합니다. v1 이벤트의 struct 스타일과 같습니다.
  - 단점: 직접 작성해야 합니다(연산자, Equals, GetHashCode 등 30줄 안팎). 구조체는 null이 될 수 없어서 슬롯의 "빈칸" 표현에 별도 장치가 필요합니다(아래 주의점 1).

[E. Vector3Int 재사용 (x=R, y=G, z=B)]
  - 장점: 이미 있고 덧셈, 비교, 해시, 직렬화, 인스펙터가 모두 됩니다. int라서 음수도 됩니다.
  - 단점: x/y/z가 R/G/B라는 암묵적 약속이라 코드를 읽을 때 혼동됩니다. 크기, 방향 같은 의미 없는 벡터 연산이 노출됩니다. 4번째 채널이 필요해지면 대체할 만한 타입이 마땅치 않습니다.

[F. 별도 클래스 Orb (고유 ID + 값)]
  - 장점: 같은 값의 오브를 ID로 구분할 수 있고, 나중에 오브에 값 외의 속성(출처, 종류 등)을 붙이기 쉽습니다.
  - 단점: 참조 타입이라 체크포인트 스냅샷과 저장 때 깊은 복사와 ID 재할당을 신경 써야 합니다. 지금의 요구("별개의 오브 = 슬롯 한 칸")는 슬롯 목록의 칸 하나가 오브 하나인 것으로 이미 충족되므로 ID가 꼭 필요하지는 않습니다. 오브는 추출과 합성 때만 바뀌어서 성능(GC)은 문제가 되지 않습니다. 값 외 정보가 붙을 계획이 있을 때만 의미가 있습니다.

[참고 의견: D (OrbValue 구조체)]
요구 사항(합성 덧셈, 완전 일치 판정, 저장, 인스펙터 입력, 음수 확장)을 가장 적은 코드로 만족합니다. "별개의 오브"는 슬롯 목록(칸 N개)이 해결하므로 값 타입이 별개 객체 역할을 못 하는 것은 아닙니다. F는 나중에 필요해지면 D를 필드로 포함하는 클래스로 추가할 수 있어서, D를 먼저 골라도 돌아가기 어려운 선택은 아닙니다.

[결정할 때 알아둘 점]
  1. 슬롯의 빈칸: 오브를 제출하면 그 칸이 빈칸으로 남습니다(Q142). 구조체는 null이 될 수 없고 JsonUtility는 nullable을 저장하지 못하므로, 슬롯 칸을 { 채워짐 여부, OrbValue } 같은 작은 구조체로 만들거나 (0,0,0)을 빈칸 표시로 쓰는 방법이 있습니다. 후자는 (0,0,0) 오브가 존재할 수 있으면(Q103에서 0 허용) 쓸 수 없으므로 Q440과 연결됩니다.
  2. 한도 N은 값 안에 넣지 않습니다. N은 맵별 설정(Q102)이므로 OrbValue는 순수한 값이고, 한도 검사는 맵 설정을 받는 별도 함수로 둡니다.
  3. 표시용 색 변환은 어떤 선택지를 골라도 별도 함수로 둡니다(v1 ToRGB처럼). 오브젝트 색 ↔ 오브 값 규칙은 3단계 질문(Q262)에서 다룹니다.

Q147. [핵심] 제출 유효성 판정의 소유자와 요구 값의 저장 위치

무엇을 정하는 질문인가: (원문 질문이 모호하게 적혀 있어서 다시 정리했습니다.) 문/목적지/작동기가 요구하는 오브 값을 어디에 저장하고, 제출된 오브와 맞는지의 판정을 누가 하며, 결과(성공/거부 + 실패 안내)를 누가 UI와 다른 기물에 전달하는지입니다.

[이미 정해진 전제]
  - 정확히 일치(R, G, B 모두)하는 오브 1개를 냅니다. 틀리면 페널티 없이 거부하고 안내 정보를 줍니다. (1차 Q26, 1단계 Q144)
  - 문은 낸 오브를 보관하는 동안 열려 있고, 오브를 회수하면 다시 닫힙니다. 목적지는 맵당 1개이고 제출하면 클리어입니다. (1단계 Q146, Q149, Q135)
  - 오브 제어 기물은 조준 + 좌클릭으로 UI 팝업이 열립니다. (1단계 Q122, Q143)
  - 체크포인트 스냅샷에는 문이 들고 있는 오브가 포함됩니다. (1단계 Q110)
  - 맵은 유니티 에디터의 프리팹/인스펙터로 제작합니다(1차 Q49). 나중에 "정답이 존재하는지" 검증하는 도구가 모든 제출 지점의 요구 값을 읽어야 합니다(1차 Q46).

원문의 세 번째 선택지(합성기가 제출 전에 검증)는 합성기가 어느 문에 낼 오브인지 모르고, 작동기에는 적용할 수 없으며, 합성 미리보기와도 중복되어 후보에서 뺐습니다. 원문의 두 번째 선택지(오브젝트가 정의하고 제출 지점이 조회)는 아래 B에 포함했습니다.

[코드에서 확인한 사실 (v1 방식)]
  - ColorCanvas는 targetRed/Green/Blue 필드로 목표 값을 직접 들고 CheckCondition에서 플레이어 값과 ==로 비교합니다. ColorFilterBlock도 자기 값과 Matches로 비교합니다. 즉 v1은 A 방식입니다.
  - ClearObjectBase.TryInteract가 조건을 확인하고 완료 처리를 하며, LevelManager가 모든 캔버스가 완료되면 StageCleared를 발행합니다.

[선택지]

[A. 제출 지점이 요구 값을 직접 보유하고 스스로 판정 (분산형, v1 방식)]
  - 방식: 문/목적지/작동기 컴포넌트가 requiredOrb를 인스펙터 필드로 갖고, TrySubmit(orb)에서 orb == requiredOrb를 판정해 결과를 UI에 돌려줍니다.
  - 장점: 구현이 가장 단순하고 v1 패턴(ColorCanvas)을 그대로 확장합니다. 맵 제작 때 요구 값이 그 기물 옆(프리팹 인스펙터)에 보입니다. 실패 안내에 쓸 "필요한 값"을 그 기물이 바로 UI에 줄 수 있습니다. 문이 들고 있는 오브와 개폐 상태도 같은 기물에 있어서 스냅샷 직렬화가 기물 단위로 끝납니다.
  - 단점: 판정 규칙을 바꾸고 싶을 때(정확 일치 외에 "이상", 합 조건 등. 1차 Q14에서 합성기별 규칙 추가를 예정함) 기물 종류마다 고쳐야 합니다. 판정 코드가 문/목적지/작동기에 반복될 수 있어서 공통 부모(기본 클래스나 인터페이스)로 묶어야 합니다. 정답 검증 도구는 장면의 모든 제출형 기물을 찾아 순회해야 합니다(공통 인터페이스로 해결 가능).

[B. 중앙 판정기 + 요구 값 표 (집중형)]
  - 방식: 제출 지점은 자기 ID만 알고, 맵 데이터/매니저에 요구 값 표(ID → 값)가 있어서 매니저가 판정합니다.
  - 장점: 모든 요구 값이 한 곳에 있어 검증 도구가 읽기 쉽고 규칙 변경이 한 곳에서 끝납니다. 씬을 열지 않고 맵 데이터(JSON)만으로 정답 존재 검증이 가능합니다.
  - 단점: 맵 제작자가 기물과 요구 값 표를 따로 관리하게 되어 불일치와 누락 실수가 납니다. 유니티 에디터에서 한눈에 보이지 않아 프리팹 방식과 궁합이 약합니다. v1 코드와 구조가 달라 새로 만들어야 합니다.

[C. 규칙 객체에 위임 (데이터 주도형)]
  - 방식: 제출 지점이 규칙 객체(예: ExactMatchRule { required }) 하나를 보유하고, 판정은 rule.Accepts(orb)로 위임합니다. 규칙은 인스펙터에서 고릅니다.
  - 장점: A의 단순함을 유지하면서, 나중에 다른 규칙(이상, 합 조건, 여러 색 중 하나)을 기존 코드 수정 없이 추가할 수 있습니다. 검증 도구는 규칙 객체만 질의하면 됩니다.
  - 단점: 지금은 "정확 일치" 하나뿐이라 과설계일 수 있습니다. 인스펙터 설정이 한 단계 늘어납니다.

[참고 의견: A]
지금 요구에 가장 단순하게 맞고 v1 코드를 재사용합니다. 다만 문/목적지/작동기가 공통 기본 클래스나 인터페이스를 공유해서 판정 코드를 한 곳에 두고, RequiredOrb를 읽기 전용으로 노출하면 UI와 검증 도구의 접근 문제도 해결됩니다. 규칙이 다양해지는 시점에 C로 확장하면 됩니다.

[결정할 때 알아둘 점]
  - 이 결정은 3단계의 상호작용 인터페이스 질문(Q263)과 같이 정하는 것이 좋습니다.
  - 판정은 Q101의 OrbValue ==를 그대로 씁니다.
  - 작동기(레이저 벽)도 같은 방식으로 요구 값을 가져야 합니다. 작동기의 회수 규칙은 Q437입니다.
  - 실패 때 알려줄 정보의 범위는 Q443에서 따로 묻습니다.
