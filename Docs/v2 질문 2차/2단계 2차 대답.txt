Q262. [핵심] 오브젝트 색 ↔ 오브 값의 매핑과 표현 방식
(통합 질문: Q262 + Q227 + Q423)

무엇을 정하는 질문인가: 오브 값(R, G, B 각 0~N)을 화면의 색으로 어떻게 바꿀지(매핑 규칙)와, 값을 색 말고 숫자 등으로도 보여 줄지(표현 방식)입니다. 월드에 놓인 추출 오브젝트, 추출한 오브(HUD, 뷰모델, 합성·제출 팝업), 문/목적지의 목표 표시가 모두 이 규칙을 씁니다.

[이미 정해진 전제]
  - 채널 값은 0~N이고 N은 맵별 설정입니다(기본 5). 모든 채널이 0인 (0,0,0)은 없습니다. (1단계 Q102, Q103, 1단계 2차 대답 Q440)
  - 추출되는 오브의 값은 고정이고 오브젝트의 색과 연동됩니다. 추출한 오브젝트는 무채색으로 바뀝니다. (1차 Q18, Q19)
  - 추출 전에는 오브젝트의 색만 보고 값을 짐작해야 하고, 조준해도 값은 보이지 않습니다. 추출한 뒤에는 값을 확인할 수 있습니다. (1단계 Q141)
  - 월드는 무채색입니다(테스트 버전은 흑백 머티리얼). (1차 Q32)
  - 제출에 실패하면 필요한 값과 낸 값을 모두 보여 줍니다. (2단계 Q444)
  - 오브 값은 OrbValue 구조체이고, 표시용 색 변환은 별도 함수 하나로 둡니다. (1단계 2차 대답 Q101)
  - 뷰모델은 소지한 오브 전부를 화면 코너에 항상 띄웁니다. (2단계 Q178)

[코드에서 확인한 사실 (v1 방식)]
  - v1은 ColorStacks.ToRGB 함수 하나로 모든 기물의 색을 칠했습니다. 채널마다 따로 255 × 값 ÷ 15를 반올림합니다(StackMax = 15, 모든 스테이지 공통). 캔버스, 컬러 필터, 팔레트, 컬러 체인저, 스택 체인저, 색 스택 HUD가 모두 이 함수를 씁니다. 즉 v1은 아래 B 방식(전역 기준 선형 변환)이었습니다.
  - v1 기물은 색과 함께 '02 01 00' 같은 숫자 라벨(StackLabelFormat, 숫자마다 해당 채널 색으로 칠함)을 붙였습니다.

[선택지 1: 매핑 규칙]

[A. 맵의 N 기준 선형 변환 (채널 = 255 × 값 ÷ 그 맵의 N)]
  - 장점: 가장 단순합니다. 맵마다 0~255 밝기 범위를 전부 써서 값 차이가 최대한 크게 보입니다.
  - 단점: 같은 값이 맵마다 다른 색이 됩니다(N=3인 맵의 빨강2 = 170, N=5인 맵의 빨강2 = 102). 맵을 옮길 때마다 색 감각을 다시 익혀야 합니다. 값 1이 아주 어둡습니다(N=5에서 51/255로 거의 검정이라 무채색 월드에서 잘 안 보임). (1,0,1)과 (2,0,2)처럼 비율이 같은 조합은 밝기만 달라서 구분이 어렵습니다.

[B. 전역 기준 선형 변환 (채널 = 255 × 값 ÷ 모든 맵 공통의 기준값)]
  - 장점: 같은 값은 어느 맵에서나 같은 색이라 한 번 익힌 규칙이 계속 통합니다(v1 방식). 변환 함수 하나로 끝납니다.
  - 단점: 기준값(모든 맵의 N 중 최댓값)을 미리 정해야 하고, 나중에 더 큰 N의 맵을 만들면 기준값이 바뀌어 모든 맵의 색이 달라집니다. 맵의 N이 기준값보다 작으면 그 맵은 어두운 쪽 색만 씁니다. 값 1이 어두운 문제와 비율이 같은 조합 문제는 A와 같습니다(아래 참고 의견의 '최소 밝기'로 완화).

[C. 고정 팔레트 (값 조합마다 색을 표로 지정)]
  - 장점: 색을 하나하나 손으로 골라 서로 잘 구분되게 만들 수 있습니다.
  - 단점: N=5면 조합이 6×6×6−1 = 215개라 전부 고를 수 없습니다. 채널별 표(빨강 1~5의 밝기 등)로 줄이면 결국 B에 밝기 곡선을 붙인 것과 같습니다. 합성으로 새로 생기는 조합도 모두 표에 있어야 합니다.

[D. 오브젝트마다 [색, 오브 값] 쌍을 직접 설정]
  - 장점: 맵 제작과 아트의 자유도가 가장 높습니다.
  - 단점: 색과 값 사이에 일정한 규칙이 없어 "색을 보고 값을 짐작"(1단계 Q141)할 수 없게 됩니다. 색과 값을 따로 입력하므로 둘이 어긋나는 실수가 생깁니다. 추출한 오브, 합성 결과, 목표 표시의 색은 어차피 규칙으로 정해야 해서 규칙이 두 개가 됩니다.

[E. 오브젝트 색만 칠하면 게임이 값을 자동 역산]
  - 장점: 맵 제작자는 색만 고르면 됩니다.
  - 단점: 색에서 값을 거꾸로 계산하려면 결국 A나 B 같은 규칙이 있어야 하고, 규칙에 딱 맞지 않는 색을 고르면 반올림으로 엉뚱한 값이 조용히 들어갑니다. 값을 직접 입력하는 것보다 실수가 잦습니다.

[F. 합성·정규화한 RGB (비율만 표시, 가장 큰 채널을 항상 최대 밝기로)]
  - 장점: 색이 항상 밝고 선명해서 무채색 월드에서 잘 보입니다.
  - 단점: 크기 정보가 사라집니다. (1,0,0)과 (5,0,0)이 같은 색이고 (1,0,1)과 (2,0,2)도 같은 색이라, 색으로 값을 짐작할 수 없습니다(1단계 Q141과 충돌). 숫자를 함께 보이지 않으면 쓸 수 없습니다.

[선택지 2: 표현 방식]

1단계 Q141 때문에 월드에 놓인 추출 전 오브젝트에는 숫자 라벨이나 값을 알려 주는 아이콘을 붙일 수 없습니다(조준해도 값이 보이지 않아야 함). 그래서 아래 선택지는 주로 추출한 오브(HUD, 뷰모델, 합성·제출 팝업)를 어떻게 보일지입니다. 문/목적지의 목표 라벨에 숫자를 보일지는 3단계 Q224에서 묻습니다.

[혼합색만]
  - 장점: 화면이 깔끔하고 '색 퍼즐'이라는 느낌이 가장 강합니다.
  - 단점: 추출한 뒤에도 정확한 값을 알기 어렵습니다. "추출한 뒤에는 값을 확인할 수 있다"(1단계 Q141)를 지키려면 팝업 등 어딘가에는 숫자가 필요합니다. 밝기만 다른 비슷한 색을 실수로 고르기 쉽습니다.

[숫자 라벨만]
  - 장점: 값이 정확합니다. 색각 이상 플레이어도 문제없습니다.
  - 단점: 색 게임의 느낌이 약해지고, 월드 오브젝트(색만 보임)와 소지 오브(숫자만 보임)의 연결이 끊깁니다.

[혼합색 + 숫자 라벨]
  - 장점: 색으로 대략 보고 숫자로 확인합니다. 월드 오브젝트와 같은 색이라 "이 오브가 저 오브젝트에서 나왔다"를 바로 알 수 있습니다. 색각 이상 대응(5단계 Q408)도 함께 해결됩니다.
  - 단점: 슬롯이 많으면 화면이 복잡해집니다(뷰모델이 소지 오브를 모두 띄우므로 숫자를 어디에 붙일지 정해야 함). 라벨 형식은 5단계 Q403에서 정합니다.

[아이콘/심볼 (예: 빨강1 = 빨간 기둥)]
  - 장점: 모양으로도 구분되어 색각 이상 대응이 됩니다.
  - 단점: 값마다 다른 모양을 만들어야 하고 조합이 많아 감당하기 어렵습니다. 월드 오브젝트에 쓰면 값이 드러나서 1단계 Q141과 충돌합니다.

[참고 의견: 매핑은 B + 최소 밝기, 표현은 월드 오브젝트 = 색만 / 추출한 오브 = 색 + 숫자]
  - 매핑: 같은 값은 어디서나 같은 색이어야 "색을 보고 짐작"하는 감각이 맵을 넘어 쌓입니다. 값 1이 너무 어두운 문제는 값 1~5를 밝기 80~255에 고르게 나눠 담으면(0→0, 1→80, 2→124, 3→168, 4→211, 5→255) 완화됩니다(80은 예시이고 테스트하며 조정). 기준값은 지금 5로 정하고 맵의 N은 5 이하로 쓰는 것을 권합니다(N=3인 맵은 1→80 ~ 3→168만 씀). 더 큰 N이 필요해지면 그때 기준값을 바꾸고 모든 맵의 색이 함께 바뀝니다.
  - 표현: 월드 오브젝트는 1단계 Q141 때문에 색만 씁니다. 추출한 오브는 HUD/뷰모델/팝업에서 색 + 숫자로 보여 줍니다. 실패하면 값을 모두 보여 주므로(2단계 Q444) 소지 오브의 숫자를 숨길 이유가 적고, 숫자가 있으면 색각 이상 대응도 됩니다.

[결정할 때 알아둘 점]
  1. 비율이 같은 조합: (1,0,1)과 (2,0,2)처럼 비율이 같으면 A, B 어느 규칙에서도 색조가 같고 밝기만 다릅니다. 조명 아래에서는 밝기 차이를 알아보기 어려우므로, 조명의 영향을 받지 않는 발광 표현(5단계 Q396)을 쓰거나, 맵 제작 때 이런 쌍을 가까이 두지 않는 규칙을 둘 수 있습니다.
  2. 세 채널이 같은 값: (1,1,1), (2,2,2) 같은 값은 어떤 선형 규칙에서도 회색이 되어, 무채색 월드나 이미 추출한(무채색으로 바뀐) 오브젝트와 헷갈립니다. 발광, 추출 후 표현(6단계 Q170, Q174), 무채색 월드에서 색 오브젝트를 구분하는 방법(4단계 Q196)과 함께 풀어야 합니다.
  3. 색각 이상 대응은 5단계 Q408, 숫자 라벨 형식은 5단계 Q403, 색과 숫자의 혼용은 5단계 Q380, 한도 근처 값의 표현은 6단계 Q412에서 묻습니다. 여기서 정한 방향에 맞춰 답하면 됩니다.
  4. 매핑 규칙은 색 변환 함수 하나에만 들어가므로(1단계 2차 대답 Q101) A, B, C 사이는 나중에 바꿔도 그 함수만 고치면 됩니다. D는 오브젝트마다 데이터가 들어가서 나중에 바꾸기 어렵습니다.

답:매핑 규칙 - 합성 정규화 rgb + 밝기는 오브젝트별로 설정(아트의 편의성), 표현 방식 - 혼합색만 표시

Q266. [핵심] 기물 간 통신 구조

무엇을 정하는 질문인가: v2의 기물(추출 오브젝트, 합성기, 문, 작동기, 레이저 벽, 목적지, 체크포인트)과 시스템(UI, 소리, HUD, 체크포인트 저장·복귀)이 서로 어떻게 알리고 호출할지입니다. 예를 들어 "작동기에 오브 제출 → 레이저 벽 꺼짐 → 소리·UI 반응"이나 "체크포인트에 닿음 → 맵 전체 상태 저장"을 누가 어떻게 연결하는지입니다.

[이미 정해진 전제]
  - 제출 판정은 제출 지점이 직접 하고(공통 기본 클래스 SubmittableObjectBase), 각 기물은 응답만 오버라이드합니다. 판정 결과는 제출 팝업에 바로 돌려줍니다. (1단계 Q147, 2단계 Q263)
  - 작동기에 오브를 제출하면 레이저 벽이 꺼지고, 회수 가능으로 설정한 작동기에서 회수하면 다시 켜집니다. (1차 Q27, 1단계 2차 대답 Q437)
  - 목적지는 맵당 1개이고 제출하면 클리어입니다. (1단계 Q135)
  - 체크포인트 스냅샷은 플레이어 위치, 소지 오브, 제출 상태, 추출 상태입니다. 맵 재시작과 체크포인트 복귀는 코드에서 두 경로입니다. (2단계 Q260, Q291)
  - LevelManager는 폐기하고(2단계 Q296), ProgressManager의 기능은 맵 안의 진행(맵 매니저)과 전역 진행(GameManager)으로 나눕니다(2단계 Q293).

[코드에서 확인한 사실]
  - Framework.Core의 EventBus는 이벤트 타입(IEvent를 구현한 타입, v1은 모두 struct)별로 구독자를 모아 두고, Publish할 때 구독자를 하나씩 개별 try/catch로 부릅니다. 한 구독자가 예외를 내도 나머지는 계속 받습니다.
  - v1에서는 13개 파일이 EventBus를 구독했고, 기물끼리 서로를 직접 참조하지 않았습니다. 예: 필터는 ColorStackChanged를 받아 통과 여부를 바꾸고, LevelManager는 CanvasCompleted를 받아 모든 캔버스가 끝나면 클리어를 발행했습니다.
  - v1에는 "이 기물이 저 기물을 켠다" 같은 1:1 연결이 없었습니다. v2의 작동기 → 레이저 벽이 첫 1:1 연결입니다.

[선택지]

[A. 이벤트 중심 (v1 방식 확장)]
  - 방식: 기물은 상태가 바뀌면 이벤트를 발행하고, 반응할 쪽이 구독합니다. 작동기는 "작동기 상태 바뀜" 이벤트를 내고, 레이저 벽은 그 이벤트를 받아 자기 작동기인지 ID로 확인한 뒤 켜지거나 꺼집니다.
  - 장점: 기물끼리 서로를 몰라서 결합이 느슨합니다. 소리, UI, HUD 같은 반응을 기존 코드 수정 없이 구독만으로 붙일 수 있습니다. v1과 같은 방식이라 익숙합니다.
  - 단점: EventBus는 전역이라 "이 작동기 → 저 레이저 벽" 같은 1:1 연결에 ID 짝 맞추기가 필요합니다. ID 오타나 누락 같은 설정 실수가 생기고, 인스펙터에서 연결이 보이지 않아 추적이 어렵습니다. 이벤트는 '알림'이라 체크포인트 스냅샷처럼 맵 전체 상태를 '모으는' 일에는 맞지 않아, 결국 씬의 기물을 찾아 순회하는 코드가 따로 필요합니다. 구독 순서에 따라 결과가 달라지는 버그가 생길 수 있습니다.

[B. 맵 매니저 중심]
  - 방식: 맵마다 맵 매니저 하나가 그 맵의 모든 기물을 참조하고, 연쇄 동작(작동기 → 레이저 벽), 스냅샷 저장·복원, 재시작, 클리어 처리를 직접 호출합니다.
  - 장점: 맵 전체 상태가 한 곳에 있어 스냅샷·복원·재시작이 간단합니다. 흐름을 따라가기 쉽습니다.
  - 단점: 맵 매니저가 모든 기물 종류를 알아야 해서 기물이 늘수록 커집니다. 새 기물을 추가할 때마다 매니저를 고쳐야 합니다. UI와 소리까지 매니저가 직접 부르면 결합이 강해집니다.

[C. 하이브리드 (연결은 직접 참조, 맵 상태는 맵 매니저, 알림은 이벤트)]
  - 방식: 세 가지를 용도별로 나눕니다.
      기물 사이의 연결(작동기 → 레이저 벽): 인스펙터 필드로 직접 연결합니다(작동기가 자기 레이저 벽을 참조해 켜고 끔. 여러 작동기가 모두 켜져야 하는 AND 조건이 필요하면 레이저 벽이 작동기 목록을 참조).
      맵 전체 상태(스냅샷 저장·복원, 재시작, 클리어): 맵 매니저가 맡습니다. 기물은 시작할 때 맵 매니저에 스스로 등록하고, 맵 매니저는 기물 종류를 몰라도 '상태 내보내기/불러오기' 인터페이스로 저장·복원합니다.
      알림(소리, UI, HUD, 클리어 화면): EventBus 이벤트로 발행합니다.
  - 장점: 연결이 인스펙터에서 보이고 ID가 필요 없습니다. 맵 매니저는 기물 종류를 몰라도 되어 커지지 않습니다. 소리와 UI는 v1처럼 구독만으로 붙습니다. 4단계 Q270(여러 작동기의 AND 조건)도 작동기 목록 참조로 간단히 됩니다.
  - 단점: 방식이 세 가지라 "무엇을 어디에 쓰는지" 규칙을 지켜야 합니다. A보다 처음 만들 코드가 조금 많습니다.

[참고 의견: C]
작동기 → 레이저 벽 연결은 맵 제작 때 인스펙터에서 바로 보이는 쪽이 실수가 적고, 체크포인트 스냅샷(2단계 Q260)은 맵 전체 상태를 한 번에 모아야 해서 등록 목록을 가진 맵 매니저가 필요합니다. 소리와 UI는 v1처럼 이벤트로 붙이면 기물 코드를 건드리지 않고 연출을 바꿀 수 있습니다. 맵 매니저가 기물 종류를 모르게 하면(등록 + 상태 내보내기/불러오기) B의 단점인 비대화도 피할 수 있습니다.

[결정할 때 알아둘 점]
  1. 맵 매니저를 둘지: 2단계 Q296(LevelManager)에서 고른 선택지의 설명은 "폐기 (각 시스템이 독립적으로 동작)"이고, Q293(ProgressManager)에서 고른 선택지의 설명은 "기능 분할 (맵별 진행은 각 맵 매니저, 글로벌은 GameManager)"이라 방향이 다릅니다. A를 고르면 Q296의 설명대로 맵 매니저 없이 각 기물이 독립적으로 동작하고, 스냅샷은 씬의 기물을 찾아 모읍니다. B나 C를 고르면 Q293의 설명대로 새 맵 매니저를 둡니다(LevelManager 코드는 재사용하지 않음).
  2. 어떤 이벤트를 만들지는 바로 다음 Q267에서 묻습니다. 여기서 A를 고르면 기물 사이의 연결과 상태 변화도 모두 이벤트가 되므로 Q267의 이벤트가 더 많아집니다.
  3. 체크포인트 복귀를 씬 재로드로 할지 오브젝트별 복원으로 할지(4단계 Q307)도 이 구조와 연결됩니다. 기물마다 '상태 내보내기/불러오기'가 있으면 씬을 다시 불러온 뒤 적용하든 그 자리에서 복원하든 둘 다 쉽습니다.
  4. 4단계 Q277(기물의 활성/비활성 상태 전환), Q278(제출한 오브의 사용 여부 추적)도 이 결정에 맞춰 답하면 됩니다.

답:하이브리드

Q267. [핵심] EventBus 이벤트 설계 범위
(통합 질문: Q267 + Q271)

무엇을 정하는 질문인가: v2에서 EventBus로 발행할 이벤트를 어디까지 만들지(이벤트 범위)와, 문·레이저 벽·작동기의 상태 변화(열림/닫힘, 켜짐/꺼짐)를 어떻게 알릴지(이벤트 없이 필드 검사 / 전용 이벤트 / v1의 MapObjectUsed 재사용)입니다.

[이미 정해진 전제]
  - 합성에는 '실패'가 없습니다. 한도를 넘게 되는 오브는 처음부터 선택할 수 없습니다. (1단계 Q127, 1단계 2차 대답 Q442) 그래서 원문 선택지의 SynthesizeFailed는 필요 없습니다.
  - 슬롯이 가득 차면 추출할 수 없습니다(1단계 Q148). 원문의 SlotFull은 이 '추출 거부'를 알리는 이벤트에 해당하고, 피드백 방식은 5단계 Q229에서 묻습니다.
  - 제출 결과(성공/거부 + 실패 안내)는 제출 지점이 팝업에 바로 돌려줍니다. (1단계 Q147)
  - 스테이지 가이드와 마커는 제거하고, 맵 에디터는 메인 시스템을 만든 뒤에 고칩니다. (1차 Q37, Q38, Q45)

[코드에서 확인한 사실]
  - v1 이벤트는 6개이고 모두 struct입니다: StageCleared, CanvasCompleted, MapObjectUsed, ColorStackChanged, ColorStackChangeRequest, InteractableTargetChanged. 여기에 패키지의 SceneLoadCompleted를 함께 썼습니다.
  - MapObjectUsed(기물이 사용됨)를 받는 곳은 StageGuideController(가이드)와 맵 에디터의 플레이 테스트(정답 순서 자동 기록) 두 곳뿐입니다. 가이드는 제거되고 맵 에디터는 나중에 고치므로, v2 초기에는 이 이벤트를 받는 곳이 없습니다.

[선택지 1: 이벤트 범위]

[최소한 (OrbCollected, OrbSynthesized, OrbSubmitted)]
  - 장점: 정의할 것이 적습니다.
  - 단점: 문이 열릴 때의 소리, 체크포인트 저장 알림, 클리어 화면처럼 오브 동작이 아닌 반응을 붙일 방법이 따로 필요합니다. 결국 하나씩 추가하게 됩니다.

[중간 (위 + DoorOpened, CheckpointReached, MapInitialized)]
  - 장점: 코어 루프와 진행(체크포인트, 맵 초기화)의 주요 지점을 덮습니다.
  - 단점: 오브 회수(문/작동기에서 되찾기), 레이저 벽 켜짐/꺼짐, 슬롯이 가득 차 추출이 거부될 때, 클리어처럼 빠진 지점이 남습니다.

[상세 (위 + SlotFull, SynthesizeFailed 등)]
  - 장점: 거의 모든 반응을 이벤트로 붙일 수 있습니다.
  - 단점: SynthesizeFailed처럼 일어나지 않는 일의 이벤트까지 만들게 되고, 받는 곳이 없는 이벤트는 유지 비용만 듭니다.

[선택지 2: 기물 상태 변화를 알리는 방법]

[이벤트 없이 필요한 곳에서 필드를 검사]
  - 장점: 이벤트 정의가 필요 없습니다.
  - 단점: UI나 소리가 매 프레임 기물을 들여다봐야 하고, 순간적인 변화를 놓칠 수 있습니다. UI가 기물을 직접 알아야 합니다.

[전용 이벤트 발행 (GateStateChanged, ActuatorActivated 등)]
  - 장점: 무엇이 바뀌었는지 타입으로 분명하고, 받는 쪽은 관심 있는 이벤트만 구독합니다. v1의 이벤트 스타일(struct)과 같습니다.
  - 단점: 이벤트 타입 수가 늘어납니다.

[v1처럼 MapObjectUsed 하나만 쓰고 종류를 필드로 구분]
  - 장점: 이벤트 타입이 하나라 정의가 적습니다.
  - 단점: 받는 쪽마다 종류를 나눠 처리해야 하고, 종류가 늘면 모든 수신 코드를 고쳐야 합니다. v1에서 이 이벤트를 받던 두 곳이 v2 초기에는 없어서 재사용할 이유가 약합니다.

[참고 의견: 받는 곳이 있는 이벤트만, 상태 변화는 전용 이벤트로]
범위를 미리 정하기보다 "받는 곳(소리, UI, HUD, 저장)이 있는 이벤트만 만든다"를 규칙으로 두는 것을 권합니다. Q266에서 C를 고르면 지금 필요한 것은 대략 다음 정도입니다. 이름은 기물 이름을 확정할 때(2단계 Q265) 맞춥니다.
  - SlotsChanged: 슬롯 내용이 바뀔 때마다(추출, 합성, 제출, 회수, 체크포인트 복귀, 재시작). HUD와 뷰모델이 받습니다(v1 ColorStackChanged와 같은 역할).
  - OrbExtracted / ExtractBlocked: 추출 연출·소리 / 슬롯이 가득 차 추출 거부(5단계 Q229의 피드백).
  - OrbSynthesized: 합성 연출·소리.
  - OrbSubmitted / OrbRetrieved: 제출·회수 소리.
  - GateStateChanged: 문·레이저 벽의 열림/닫힘 연출·소리.
  - CheckpointReached: 체크포인트 저장 알림(5단계 Q398).
  - MapCleared: 클리어 화면.
제출 거부(실패 안내)는 제출 지점이 팝업에 바로 돌려주므로 이벤트가 필요 없습니다.

[결정할 때 알아둘 점]
  1. Q266에서 A(이벤트 중심)를 고르면 작동기 → 레이저 벽 연결도 이벤트가 되어 ActuatorStateChanged 같은 이벤트가 더 필요합니다. C를 고르면 그 연결은 직접 참조라 이벤트가 필요 없습니다.
  2. 4단계 Q278(제출한 오브의 사용 여부 추적)은 이 질문과 같은 주제이니 함께 답하면 됩니다.
  3. EventBus는 구독자 하나가 예외를 내도 나머지는 계속 받으므로, 소리와 UI를 이벤트로 붙여도 연출 쪽 오류가 게임 진행을 멈추지 않습니다.

답:받는 곳(소리, UI, HUD, 저장)이 있는 이벤트만 만든다

Q450. [보통] 체크포인트 세부

체크포인트는 프리팹으로 배치하고 플레이어가 닿으면 자동으로 활성화됩니다(2단계 Q179, Q295). 일시정지 메뉴에는 '체크포인트로' 버튼이 있습니다(Q184). 남은 세부입니다.

  [같은 체크포인트에 다시 닿으면]
    - 닿을 때마다 그 순간의 상태로 다시 저장
    - 처음 닿을 때만 저장 (이미 활성화된 체크포인트는 무시)
  [복귀할 때 플레이어의 시선]
    - 체크포인트 오브젝트가 정한 방향
    - 저장 당시 플레이어가 보던 방향

    - '처음부터'와 같게 동작 (맵 시작 상태로 복귀)
    - 기타

다시 저장하는 방식이면, 막힌 상태(잘못 합성한 오브 등)로 체크포인트를 다시 밟았을 때 그 상태가 저장되어 '처음부터'로만 빠져나올 수 있습니다. 처음 닿을 때만 저장하는 방식이면, 앞쪽 체크포인트로 되돌아가 밟아도 저장되지 않습니다.

Q452. [핵심] v2 저장 데이터를 SaveManager의 어느 파일에 넣을지

2단계 Q297에서 Framework.Core의 SaveManager를 계속 쓰기로 했습니다(고른 선택지의 설명: "ColorMaze 전용 데이터는 extension으로 추가"). v2 저장 데이터는 맵별 클리어 기록 + 현재 맵의 마지막 체크포인트 1개 + 시맨틱 버전 필드입니다(1단계 Q105, 1단계 2차 대답 Q436, 2단계 Q289). 이 데이터를 패키지의 어느 기능으로 어느 파일에 저장할지 정해야 합니다.

[코드에서 확인한 사실]
  - SaveManager의 저장 방법은 두 가지입니다. (1) 진행 저장 API: 패키지 안의 SaveData 클래스를 항상 save.json에 저장합니다(Current, Save, Load, HasSave, Delete). 게임 시작 때 자동으로 Load합니다. (2) 범용 JSON API: 아무 [Serializable] 타입을 원하는 파일 이름으로 저장합니다(SaveJson, LoadJson, HasJson, DeleteJson. 실패해도 예외를 던지지 않음).
  - 패키지의 SaveData에는 level, gold, playTime, lastScene, unlockedChapterCount, clearedStages가 있고 버전 필드는 없습니다. 클래스 주석은 "게임에 맞게 필드를 추가해 쓴다"이지만, 이 패키지는 git으로 받아오는 공용 패키지라 필드를 추가하려면 패키지 저장소를 고쳐야 하고 다른 프로젝트도 같은 클래스를 씁니다.
  - v1은 이미 범용 JSON API로 settings.json(설정), stage_attempts.json(시도 횟수), CustomMap_*.json(맵 에디터 맵)을 따로 저장합니다.
  - v1 설정 화면의 저장 초기화(확인 창을 거침)는 SaveManager.Delete()로 save.json만 지웁니다.

[A. ColorMaze 전용 저장 클래스 + 범용 JSON API로 별도 파일 (예: colormaze_save.json)]
  - 장점: 패키지를 고치지 않습니다. 버전 필드와 체크포인트를 자유롭게 넣습니다. v1 save.json을 읽지 않으므로 1차 Q43(v1 저장 리셋)은 v2가 새 파일로 시작하는 것으로 자연히 충족됩니다. v1이 settings.json 등에 이미 쓰는 방식이라 익숙합니다.
  - 단점: 패키지의 진행 저장 API(Current, Save)는 쓰지 않게 됩니다(시작 때 save.json을 읽기는 하지만 무해). v1 save.json 파일은 플레이어 PC에 그대로 남습니다(백업·삭제는 4단계 Q311). 설정 화면의 저장 초기화가 새 파일을 지우도록 고쳐야 합니다.

[B. 클리어 기록은 패키지 SaveData의 clearedStages(맵 이름 목록)를 그대로 쓰고, 체크포인트만 별도 파일]
  - 장점: MarkStageCleared, IsStageCleared를 그대로 재사용합니다.
  - 단점: 저장 데이터가 두 파일로 나뉘어, 한쪽만 저장된 채 꺼지면 어긋날 수 있습니다. 버전 필드는 체크포인트 파일에만 넣을 수 있습니다. v1 save.json의 clearedStages에 v1 스테이지 이름이 남아 있어 v2 첫 실행 때 지워야 하는데(1차 Q43), save.json에는 버전 필드가 없어 v1 파일인지 구분하기 어렵습니다.

[C. 패키지 SaveData에 v2 필드(체크포인트, 버전)를 추가]
  - 장점: 진행 저장 API(Current, Save)를 그대로 씁니다. 클래스 주석의 의도("필드를 추가해 쓴다")와 맞습니다.
  - 단점: 공용 패키지에 ColorMaze 전용 필드가 들어가 다른 프로젝트의 저장 데이터에도 생깁니다. 패키지 저장소를 수정하고 버전을 올려야 합니다. v1 save.json과 같은 파일이라 v1 데이터를 리셋(1차 Q43)하는 처리가 따로 필요합니다.

[D. 패키지 SaveManager를 고쳐 프로젝트마다 자기 SaveData 타입을 지정하게 함 (제네릭화)]
  - 장점: 패키지를 쓰는 모든 프로젝트가 자기 저장 클래스를 깔끔하게 쓸 수 있는 가장 정돈된 구조입니다.
  - 단점: 작업량이 가장 많고, 패키지를 쓰는 다른 프로젝트도 함께 고쳐야 합니다. 지금 v2에 꼭 필요한 일은 아닙니다.

[참고 의견: A]
패키지를 건드리지 않고, v1이 설정·시도 횟수·맵 에디터 맵에 이미 쓰는 방식 그대로라 새로 익힐 것이 없습니다. Q297에서 고른 선택지의 "extension으로 추가"에도 맞습니다. 버전 필드를 처음부터 넣을 수 있어 나중에 저장 형식이 바뀌어도 판단할 수 있습니다. A나 B를 고르면 지금까지 답에 나온 'save.json'은 'v2 저장 파일'이라는 뜻으로 바꿔 읽으면 됩니다.
