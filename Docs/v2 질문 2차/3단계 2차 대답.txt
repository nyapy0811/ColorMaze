Q321. [핵심] WallNodeEntry 데이터 구조

무엇을 정하는 질문인가: 벽 노드와 노드 사이의 벽(연결)을 맵 데이터에 어떤 모양으로 저장할지입니다. 데이터를 어디에 둘지(선택지 1), 노드끼리의 연결을 어떻게 적을지(선택지 2), 좌표에 높이를 넣을지(선택지 3)를 정합니다. 맵 파일의 저장·불러오기, 벽 프리팹을 놓는 코드, 인게임 맵 에디터, 정답 검증 도구가 모두 이 구조를 읽습니다.

[이미 정해진 전제]
  - 노드 좌표는 정수 그리드, 월드 1유닛입니다. 어느 두 노드든 직선 벽으로 이을 수 있습니다(대각선 포함, 예: (1,1)과 (3,5)). (3단계 Q320)
  - 한 노드는 여러 노드와 이어질 수 있습니다(분기·교차 가능). (3단계 Q322)
  - 벽은 메시를 만들지 않고, 노드 데이터에 따라 벽 프리팹과 코너 프리팹을 배치합니다. (3단계 Q323)
  - 인게임 맵 에디터(UGC)도 같은 CustomStageData 형식을 씁니다. (3단계 Q324)
  - 문처럼 벽으로 취급할 수 있는 기물은 노드 시스템에 넣고, 그 밖의 기물은 설치형입니다. (3단계 Q326)
  - 기존 유저 제작 맵(CustomMap_*.json)은 그대로 보존합니다. (1차 Q44)
  - 삭제한 v1 타입을 참조하는 맵 에디터 코드는 더미 enum·더미 클래스(스텁)로 컴파일을 유지합니다. (3단계 Q414)

[코드에서 확인한 사실]
  - CustomStageData(맵 하나의 전체 데이터)는 id(GUID 문자열), title, blocks(BlockEntry 목록), fixtures(FixtureEntry 목록), canvasOrders(캔버스별 정답 순서), clearVerified(플레이 테스트로 클리어를 확인했는지)를 가집니다. 버전 필드는 없습니다.
  - BlockEntry는 블록 한 칸의 정수 좌표(x, y, z)만 가집니다. 이웃과의 연결 정보는 없습니다.
  - FixtureEntry는 기물 하나의 배치입니다: 맵 안에서만 유효한 정수 id, 종류(FixtureType enum, v1 기물 7종), 좌표(x, y, z), v1 기물용 파라미터. 한 점에 놓이는 기물을 위한 구조입니다.
  - 데이터 사이의 참조(캔버스 → 정답 순서의 기물들)는 리스트 위치가 아니라 이 정수 id로 합니다. 편집 중에 기물을 지우거나 다시 놓아도 참조가 깨지지 않게 하기 위해서입니다.
  - JsonUtility로 저장하므로 Dictionary는 쓸 수 없고 모두 List 기반입니다(클래스 주석에 적혀 있음).

[선택지 1: 데이터를 둘 곳]

[A. CustomStageData에 노드 목록과 벽 목록을 새로 추가 (원문 첫 번째 선택지)]
  - 방식: 노드(WallNodeEntry)와 벽(두 노드를 잇는 것, 예: WallEntry) 타입을 새로 만들고 CustomStageData에 nodes, walls 목록을 추가합니다. blocks와 fixtures는 그대로 둡니다.
  - 장점: 맵 하나가 파일 하나로 남아 3단계 Q324의 '같은 형식'에 그대로 맞습니다. 기존 필드를 바꾸지 않으므로 v1 유저 맵 파일도 형식이 깨지지 않습니다(새 목록이 빈 채로 읽힘). 벽(nodes, walls)과 설치형 기물(fixtures)이 같은 파일 안에서 나뉘어 3단계 Q326의 구분과 맞습니다.
  - 단점: CustomStageData에 v1용 필드(blocks, canvasOrders)와 v2용 필드가 함께 남습니다. v1 필드를 언제 정리할지는 맵 에디터를 고칠 때(1차 Q45) 정해야 합니다.

[B. BlockEntry를 WallNodeEntry로 이름만 바꾸고 구조 유지]
  - 장점: 새 타입을 거의 만들지 않아 변경이 가장 적어 보입니다.
  - 단점: BlockEntry에는 좌표만 있어서 어느 노드와 어느 노드 사이에 벽이 있는지 담을 곳이 없습니다. 결국 연결 목록을 따로 추가해야 하므로 A와 같아집니다. 또 v1 블록은 1×1×1 칸이고 노드는 점이라 뜻이 다릅니다. 필드 이름(blocks)을 그대로 두면 v1 유저 맵의 블록 좌표가 노드로 읽혀 엉뚱한 벽이 생기고, 필드 이름까지 바꾸면 새 목록을 만드는 A와 같습니다.

[C. FixtureEntry를 확장해 '벽 기물' 종류로 통합]
  - 방식: FixtureType에 벽 종류를 추가하고, FixtureEntry에 '이어지는 다른 점' 필드를 더합니다.
  - 장점: 목록이 하나라 저장·불러오기 코드도 하나입니다. 문·레이저 벽처럼 '기물이면서 벽'인 것과 일반 기물을 한 목록에서 다룹니다.
  - 단점: FixtureEntry는 한 점에 놓이는 기물 구조라, 두 점을 잇고 한 노드를 여러 벽이 함께 쓰는 연결(3단계 Q322)과 맞지 않습니다. 한 노드에 벽이 여러 개 붙으면 그 노드 좌표가 여러 항목에 중복되어, 노드 하나를 옮길 때 모든 항목을 함께 고쳐야 합니다. FixtureType은 v1 기물 enum이라 더미로 남겨 두기로 했는데(3단계 Q414) 여기에 v2 종류를 넣으면 v1과 v2가 한 enum에 섞입니다. 3단계 Q326의 노드 시스템 / 설치형 구분도 데이터에서는 사라집니다.

[D. CustomStageData와 따로 WallNodeData 클래스(파일)를 둠]
  - 방식: 벽 노드 데이터만 별도 클래스로 만들고 맵마다 파일을 하나 더 둡니다.
  - 장점: 벽 데이터를 다른 맵 데이터와 독립적으로 고치거나 다시 쓸 수 있습니다(같은 벽 배치를 여러 맵에 쓰는 경우 등).
  - 단점: 맵 하나가 파일 두 개가 되어, 한쪽만 저장되거나 둘이 어긋날 수 있습니다(2단계 2차 대답 Q452의 B 선택지와 같은 문제). 문의 요구 값처럼 벽과 기물에 걸치는 데이터(이 파일의 Q458)를 어느 파일에 둘지 애매해집니다. 3단계 Q324의 '같은 CustomStageData 형식'과도 어긋납니다.

[선택지 2: 노드끼리의 연결을 적는 방법]

[가. 벽 목록 (벽 하나 = 양 끝 노드의 id 둘 + 벽 종류)]
  - 예: 노드 = 노드1 (1, 0, 1), 노드2 (3, 0, 5) / 벽 = 노드1 ↔ 노드2, 일반 벽
  - 장점: 벽 하나가 항목 하나라 중복이 없습니다. 벽마다 다른 설정(문·레이저 벽, 벽 프리팹 종류 등)을 그 항목에 바로 붙일 수 있습니다. 벽을 지울 때 항목 하나만 지우면 됩니다. 배치 코드는 벽 목록을 돌며 벽 프리팹을 놓고, 노드마다 붙은 벽의 수와 방향을 세어 코너 프리팹을 고릅니다.
  - 단점: 한 노드에 어떤 벽이 붙어 있는지는 불러올 때 한 번 계산해야 합니다(간단한 반복문).

[나. 노드마다 이어진 노드 목록 (이웃 목록)]
  - 예: 노드1 (1, 0, 1)의 이웃 = 노드2 / 노드2 (3, 0, 5)의 이웃 = 노드1
  - 장점: 노드를 보면 붙은 벽이 바로 보여 코너 계산이 쉽습니다.
  - 단점: 벽 하나가 양쪽 노드에 두 번 적혀서 한쪽만 고치는 실수로 어긋날 수 있습니다. 벽 하나에 설정(종류, 문의 요구 값 등)을 붙일 자리가 없어서, 문·레이저 벽을 노드 시스템에 넣으면(3단계 Q326) 결국 벽 목록이 따로 필요해집니다.

[선택지 3: 노드 좌표에 높이를 넣을지]

[(x, z)만]
  - 장점: 데이터가 가장 단순합니다. 모든 맵이 단일 층이면 충분합니다.
  - 단점: 나중에 층이나 높이 차이가 필요해지면 저장 형식이 바뀝니다.

[(x, y, z)]
  - 장점: 층이 있는 맵이나 노드마다 다른 높이(5단계 Q327)에 대비합니다. v1 BlockEntry, FixtureEntry와 같은 모양입니다. 단일 층 맵은 y를 모두 0으로 두면 됩니다.
  - 단점: 단일 층으로 확정되면 y는 쓰지 않는 값이 됩니다.

[참고 의견: A + 가 + (x, y, z)]
  - 데이터를 둘 곳(A): 맵 하나가 CustomStageData 파일 하나로 남아 3단계 Q324와 맞고, 기존 필드를 건드리지 않아 v1 유저 맵 파일도 깨지지 않습니다.
  - 연결(가): 문·레이저 벽을 노드 시스템에 넣기로 했으므로(3단계 Q326) 벽 하나에 종류와 설정을 붙일 자리가 필요합니다. 벽 목록이면 그 자리가 처음부터 있습니다.
  - 좌표((x, y, z)): 단일 층으로 할지가 아직 미정이라(1차 Q30) 높이를 넣어 두는 쪽이 안전합니다. 비용은 숫자 하나입니다.
  - 덧붙여, v2 형식을 새로 정하는 김에 CustomStageData에 버전 필드를 넣는 것을 권합니다. v2 저장 파일에 시맨틱 버전을 넣기로 한 것(2단계 Q289)과 같은 이유로, 나중에 형식이 바뀌어도 어느 형식의 맵 파일인지 알 수 있습니다. 지금 v1 맵 파일에는 버전 필드가 없으므로 '버전 필드가 없으면 v1 맵'으로 구분할 수도 있습니다.
  - 모양 예시(이름은 기물 이름을 확정할 때(2단계 Q265) 맞춤):
      노드: id, x, y, z
      벽: 양 끝 노드의 id 둘(a, b), 종류(일반 벽 / 문 / 레이저 벽), 종류별 설정(이 파일의 Q458, Q460 답에 따라)
      CustomStageData: 기존 필드 + version, nodes, walls

[결정할 때 알아둘 점]
  1. 노드 id 방식(자동 증가 / 좌표 해시 / GUID)은 5단계 Q340에서 묻습니다. 벽 목록 방식이면 노드에 id가 있으면 되고, 벽 하나를 따로 가리킬 일이 있으면(작동기 → 레이저 벽 연결 등, 이 파일의 Q458) 벽에도 id가 필요합니다.
  2. 노드 시스템에 넣을 기물과 문·레이저 벽의 형태는 이 파일의 Q460, 문의 요구 값과 작동기 연결을 어디에 둘지는 Q458, 노드 종류를 enum으로 둘지 상속 구조로 둘지는 6단계 Q357에서 묻습니다. 종류를 enum 필드 하나로 나누면 JsonUtility로 그대로 저장됩니다.
  3. 벽마다 다른 프리팹(6단계 Q354)이나 높이(5단계 Q327)를 쓰게 되면 벽 항목에 필드를 더합니다. JsonUtility는 파일에 없는 필드를 기본값으로 채우므로, 필드를 더해도 그 전에 저장한 맵 파일은 그대로 읽힙니다. 지금 다 정하지 않아도 됩니다.
  4. 유니티 에디터로 만드는 맵도 같은 노드·벽 클래스를 씬의 컴포넌트에 목록으로 들고 있으면, 인게임 맵 에디터와 같은 배치 코드를 쓰고 JSON으로 내보낼 수도 있습니다(정답 검증 도구의 입력, 3단계 Q415).
  5. 기존 유저 맵(BlockEntry 기반)을 v2에서 읽을지는 5단계 Q338, Q420에서 묻습니다. A는 그 답과 상관없이 파일 형식을 깨지 않습니다.

Q393. [핵심] 무채색 월드 구현 방식

무엇을 정하는 질문인가: 월드(벽, 바닥, 배경)를 무채색으로 보이게 하는 방법입니다. 오브와 색 오브젝트만 색을 띠고 나머지는 무채색인 화면이 이 게임의 기본 그림이라, 이 방법에 따라 머티리얼 제작 방식, 구입 에셋을 쓰는 방법, 포스트프로세싱 구성이 달라집니다.

[이미 정해진 전제]
  - 월드는 무채색입니다. 테스트 버전은 머티리얼을 흑백으로 처리하고, 최종 구현은 개발하면서 정합니다. (1차 Q32)
  - 추출한 오브젝트는 무채색으로 바뀝니다. (1차 Q18)
  - 오브젝트 색은 값의 비율을 정규화한 RGB이고, 오브젝트마다 정하는 밝기는 아트용입니다. 오브는 항상 최대 밝기입니다. (2단계 2차 대답 Q262, 3단계 Q454)
  - 세 채널이 같은 값(흰색이나 회색으로 보임)은 추출 오브젝트와 목표에 쓰지 않습니다. (3단계 Q455)
  - 목표(문·목적지·작동기가 요구하는 값)는 기물의 색으로 보입니다. (3단계 Q224) 소지 오브는 화면 우하단에 3D 오브로 보입니다. (3단계 Q221)
  - 3D 모델은 직접 제작과 에셋 구입을 병행하고(1차 Q49), 카테고리별 분담은 정하지 않았습니다(3단계 Q395).

[코드에서 확인한 사실]
  - 프로젝트는 Unity 6000.5와 URP 17.5를 쓰고, Shader Graph 17.5가 URP와 함께 들어 있습니다.
  - v1은 기물의 색을 머티리얼을 바꾸지 않고 MaterialPropertyBlock으로 _BaseColor(URP Lit/Unlit의 색 속성)만 덮어써서 칠했습니다(MapObjectBase.ApplyColorTo). 같은 머티리얼을 쓰는 기물도 저마다 다른 색을 낼 수 있는 방식입니다.
  - v1 스테이지 씬들은 볼륨 프로필 하나(Assets/Settings/SampleSceneProfile.asset)를 함께 쓰고, Bloom, Vignette, Tonemapping이 켜져 있습니다(MotionBlur는 꺼짐). 채도를 바꾸는 효과(Color Adjustments)는 없습니다.
  - TextMesh Pro 기본 셰이더를 빼면 프로젝트에서 직접 만든 셰이더는 두 개(v1 필터 테두리, 상호작용 하이라이트 외곽선)뿐입니다.

[선택지]

[A. 포스트프로세싱으로 화면 전체의 채도를 낮춤]
  - 방식: 볼륨에 Color Adjustments를 넣고 채도(Saturation)를 -100으로 둡니다.
  - 장점: 볼륨 설정 하나로 끝나 가장 빠릅니다. 구입한 에셋도 손대지 않고 무채색이 됩니다.
  - 단점: 화면 전체에 적용되므로 오브, 색 오브젝트, 목표의 색까지 함께 회색이 됩니다. 색을 보여 주는 것이 이 게임의 핵심이라 그대로는 쓸 수 없습니다. 색 오브젝트만 빼려면 렌더러 설정을 따로 만들어야 합니다(색 오브젝트를 별도 레이어로 두고 포스트프로세싱 뒤에 그리거나, 스텐실로 표시한 부분만 색을 남김). 앞의 방법은 색 오브젝트에 Bloom 같은 효과가 함께 빠지고, 뒤의 방법은 셰이더와 렌더러 기능을 직접 만들어야 해서 B보다 복잡합니다. 화면 UI(Screen Space - Overlay)는 영향을 받지 않습니다.

[B. 채도를 낮추는 셰이더를 월드 머티리얼에 씀 (Shader Graph)]
  - 방식: 텍스처 색을 흑백으로 바꿔 그리는 셰이더를 Shader Graph로 하나 만들고, 월드 머티리얼(벽, 바닥, 배경)이 이 셰이더를 쓰게 합니다. 색 오브젝트는 지금처럼 일반 URP 셰이더를 씁니다.
  - 장점: 구입한 에셋의 텍스처를 그대로 쓰면서 무채색으로 보여 디테일이 남습니다. 셰이더에 채도 값을 두면 실행 중에 바꿀 수 있어 연출(예: 클리어할 때 월드에 색이 돌아옴)도 됩니다. 화면 효과가 아니라 물체 단위라서 색 오브젝트와 섞이지 않습니다.
  - 단점: 월드 머티리얼마다 셰이더를 바꿔 줘야 합니다(구입 에셋의 머티리얼 포함). 구입 에셋이 자체 셰이더를 쓰면 그 셰이더에도 같은 처리가 필요합니다. 셰이더 하나를 만들고 관리해야 합니다.

[C. 월드 머티리얼을 회색으로 만듦 (지금의 테스트 방식)]
  - 방식: 벽, 바닥, 배경의 머티리얼 색과 텍스처를 회색조로 만듭니다.
  - 장점: 가장 단순하고 코드나 셰이더가 필요 없습니다. 테스트 버전 방식(1차 Q32)이라 바로 시작할 수 있습니다. 성능 비용이 없습니다.
  - 단점: 구입한 에셋은 텍스처를 회색조로 바꾸는 작업이 따로 필요합니다. 실행 중에 채도를 서서히 바꾸는 연출은 어렵습니다(머티리얼을 통째로 바꾸는 것은 가능).

[D. 색 정보를 다른 채널(노멀맵 등)에 인코딩]
  - 장점: 특수한 연출에는 쓰일 수 있습니다.
  - 단점: 노멀맵은 표면의 굴곡을 나타내는 데 쓰여서 색을 넣으면 조명이 깨집니다. 이 게임에서 얻는 것이 없어 맞지 않습니다(원문 선택지라 정리만 했습니다).

[참고 의견: C로 시작하고, 필요해지면 B를 더함]
  - 지금은 C로 시작해도 잃는 것이 없습니다. 직접 만드는 모델과 기본 도형은 처음부터 회색 머티리얼로 만들면 됩니다.
  - 구입한 에셋을 쓰기 시작하거나 월드에 색이 돌아오는 연출을 넣고 싶어지면, 그때 B(채도 셰이더)를 만들어 필요한 머티리얼에만 씁니다. B와 C는 물체 단위라 한 맵에서 섞어 쓸 수 있습니다.
  - A는 색 오브젝트까지 회색이 되는 문제를 피하는 구현이 가장 복잡해서 권하지 않습니다. 다만 B나 C로 무채색을 만든 뒤 분위기를 위한 약한 색 보정을 화면 전체에 더하는 것은 별개로 할 수 있습니다(5단계 Q404).

[결정할 때 알아둘 점]
  1. 무엇이 '월드'이고 무엇이 '색 오브젝트'인지 나누는 기준이 필요합니다. B와 C는 머티리얼로 나뉘고, A에서 색 오브젝트를 빼려면 레이어나 스텐실로 나눠야 합니다. 문·목적지·작동기는 요구 값의 색을 띠므로(3단계 Q224) 색 오브젝트 쪽입니다.
  2. 추출한 오브젝트의 무채색이 월드의 무채색과 같은지는 6단계 Q170, Q174, 무채색 월드에서 색 오브젝트를 돋보이게 하는 방법은 4단계 Q196, 벽을 다른 기물과 구분하는 방법은 6단계 Q348에서 묻습니다. B를 색 오브젝트에도 쓰면 추출할 때 채도를 0으로 내리는 방식으로 무채색 전환을 연출할 수도 있습니다.
  3. 포스트프로세싱을 쓸지와 어떤 효과를 쓸지는 5단계 Q404에서 묻습니다. v1 볼륨의 Bloom은 밝은 색을 번지게 하므로 오브 발광(5단계 Q396)과 함께 생각하면 됩니다. A를 고르면 Bloom의 번짐도 함께 회색이 될 수 있어 확인이 필요합니다.
  4. 어느 쪽이든 머티리얼 단위의 결정이라 나중에 바꾸기 어렵지 않습니다. C에서 B로 옮길 때는 월드 머티리얼의 셰이더만 바꾸면 됩니다.

Q458. [핵심] 노드 시스템의 벽·문·레이저 벽을 언제 실제 오브젝트로 만들지

3단계 Q323에서 벽은 노드 데이터에 따라 프리팹을 런타임에 배치하기로 했고, Q326에서 문처럼 벽으로 취급할 수 있는 기물도 노드 시스템에 넣기로 했습니다. 그런데 '런타임에 만든다'는 것은 유니티 에디터에서 맵을 편집하는 동안에는 벽·문·레이저 벽 오브젝트가 씬에 없다는 뜻이라, 앞선 결정 몇 가지와 맞지 않습니다.

[맞춰 볼 결정]
  - 작동기 → 레이저 벽 연결은 인스펙터 필드로 직접 참조합니다(2단계 2차 대답 Q266, 하이브리드). 레이저 벽이 편집 중에 없으면 작동기가 참조할 대상이 없습니다.
  - 문은 요구 값(requiredOrb)을 인스펙터 필드로 직접 가집니다(1단계 2차 대답 Q147). 문이 편집 중에 없으면 이 값을 넣을 곳이 없습니다.
  - 맵 제작은 유니티 에디터의 프리팹 방식입니다(1차 Q49). 편집하는 동안 벽이 보이지 않으면 기물을 놓을 자리를 잡기 어렵습니다.
  - 라이트맵 베이킹(6단계 Q349)은 베이킹할 때 씬에 있는 정적 오브젝트에만 됩니다. 런타임에 만든 벽에는 구운 그림자와 간접광을 쓸 수 없습니다(실시간 조명은 문제없음).
  - 인게임 맵 에디터(UGC) 맵은 파일에서 불러오므로 어느 쪽을 고르든 런타임에 만들어야 합니다(3단계 Q324).

[A. 유니티 에디터 맵은 에디터에서 미리 만들고, UGC 맵만 런타임에 만듦]
  - 방식: 노드 데이터로 벽·문·레이저 벽을 만드는 배치 코드를 하나 만들어 두 곳에서 씁니다. 유니티 에디터에서는 노드를 고칠 때(또는 버튼을 누를 때) 배치 코드가 씬에 오브젝트를 만들어 두고 씬과 함께 저장합니다. 인게임 맵 에디터 맵은 불러올 때 같은 배치 코드가 런타임에 만듭니다.
  - 장점: 편집 중에 벽이 보입니다. 미리 만든 레이저 벽과 문이 씬에 있으므로 작동기의 인스펙터 참조(2단계 2차 대답 Q266)와 문의 요구 값 필드(1단계 2차 대답 Q147)를 그대로 쓸 수 있습니다. 벽에 라이트맵을 구울 수 있습니다. 배치 코드가 하나라 두 에디터의 결과가 같습니다.
  - 단점: 노드를 고쳐 오브젝트를 다시 만들 때, 그 오브젝트에 인스펙터로 넣은 값(문의 요구 값, 작동기가 가리키는 레이저 벽)이 사라지지 않게 해야 합니다. 다시 만들 때 같은 id의 기존 오브젝트를 지우지 않고 재사용하거나, 그런 값을 노드 데이터에 두고 배치 코드가 넣어 주면 됩니다. 나중에 UGC 맵에서 작동기·레이저 벽을 지원할 때는 그 연결을 데이터(id)에 담아야 합니다(B와 같음).

[B. 어디서든 런타임에만 만듦 (3단계 Q323 그대로)]
  - 방식: 유니티 에디터 맵도 노드 데이터만 씬에 두고, 플레이를 시작할 때 배치 코드가 만듭니다.
  - 장점: 3단계 Q323 그대로이고 만드는 경로가 하나입니다. 유니티 에디터 맵과 UGC 맵이 완전히 같은 방식이라 한쪽에서 확인한 것이 다른 쪽에도 맞습니다.
  - 단점: 문의 요구 값과 작동기 → 레이저 벽 연결을 노드 데이터에 넣어야 합니다. 작동기는 레이저 벽을 인스펙터로 직접 참조하지 못하고 id로 찾게 되어, 2단계 2차 대답 Q266에서 고른 인스펙터 직접 참조를 이 연결에서는 id 연결로 바꾸게 됩니다(id 오타·누락 같은 설정 실수의 가능성). 편집 중에 벽을 보려면 노드 데이터를 선과 상자로 그려 주는 미리보기(기즈모) 코드가 따로 필요합니다. 벽에 라이트맵을 구울 수 없습니다.

[C. 문과 레이저 벽은 설치형 기물로 바꾸고, 일반 벽만 노드 시스템으로 런타임에 만듦]
  - 방식: 3단계 Q326을 바꿔 문과 레이저 벽은 씬에 프리팹으로 직접 놓습니다. 일반 벽만 노드로 런타임에 만듭니다.
  - 장점: 문과 레이저 벽이 씬에 있으므로 인스펙터 참조와 요구 값 필드를 그대로 씁니다.
  - 단점: 3단계 Q326의 답이 바뀝니다. 문이 들어갈 자리의 벽을 비우는 처리가 따로 필요합니다(벽 구간을 문 폭만큼 끊거나, 문과 겹치는 벽을 지움). 일반 벽은 여전히 편집 중에 보이지 않고 라이트맵을 구울 수 없습니다.

[참고 의견: A]
맵 제작은 유니티 에디터의 프리팹 방식이고(1차 Q49) 기물 연결은 인스펙터에서 보이게 하기로 했으므로(2단계 2차 대답 Q266), 유니티 에디터 맵은 오브젝트가 씬에 있는 편이 앞선 결정과 잘 맞습니다. 배치 코드를 하나만 두고 에디터와 런타임에서 함께 쓰면 3단계 Q323, Q324의 뜻(노드 데이터로 프리팹 배치, 두 에디터가 같은 형식)도 그대로 지켜집니다. 다시 만들 때 값을 지키는 방법은 구현할 때 정해도 됩니다.

[결정할 때 알아둘 점]
  1. A나 B를 고르면 문의 요구 값을 노드 데이터(이 파일의 Q321의 벽 항목)에 둘지가 이어서 정해집니다. C를 고르면 문과 레이저 벽은 노드 데이터에 들어가지 않습니다.
  2. 문과 레이저 벽을 노드 데이터에서 어떻게 나타낼지(구간 하나 / 일정 폭으로 끼움 등)는 이 파일의 Q460에서 묻습니다.
  3. 6단계 Q349(라이트맵·성능)는 이 답에 따라 선택지가 달라집니다. B나 C면 일반 벽에는 라이트맵 베이킹을 쓸 수 없습니다.
  4. 체크포인트 스냅샷에 문·작동기의 제출 상태를 저장할 때 무엇으로 식별할지(4단계 Q313)도 이어집니다. 노드 데이터의 id(5단계 Q340)를 쓰면 A, B 모두 같은 방식으로 식별할 수 있습니다.

Q459. [핵심] 대각선·임의 길이 벽과 코너를 프리팹으로 채우는 방법

노드는 정수 그리드 위에 있고 어느 두 노드든 직선으로 이을 수 있어서(3단계 Q320, Q322) 벽 구간의 길이가 정수가 아닐 수 있습니다. 예를 들어 (1,1)과 (3,5)를 이으면 길이가 약 4.47유닛인 대각선 벽이 됩니다. 벽은 벽 프리팹과 코너 프리팹으로 채우므로(Q323), 길이가 제각각인 구간과 여러 벽이 여러 각도로 만나는 노드를 어떻게 채울지 정해야 합니다.

  [벽 구간의 길이]
    - 벽 프리팹 하나를 구간 길이에 맞게 늘림 (텍스처는 월드 좌표 기준으로 입혀 늘어나 보이지 않게 함)
    - 1유닛짜리 벽 모듈을 반복해서 놓고, 남는 길이는 마지막 모듈을 늘리거나 줄여 채움
    - 기타
  [노드(코너) 처리]
    - 모든 노드에 같은 기둥 프리팹을 놓아 이음새를 가림 (붙은 벽의 수·각도와 상관없음)
    - 노드에 붙은 벽의 수와 각도에 맞는 코너 프리팹을 골라 놓음 (L자, T자, 십자 등)
    - 노드마다 맵 제작자가 코너 프리팹을 고름
    - 기타

늘리는 방식은 구간마다 오브젝트가 하나라 가볍지만, 일반 텍스처는 늘어나 보이므로 월드 좌표로 텍스처를 입히는 셰이더(Shader Graph의 트라이플래너 등)가 필요합니다. 반복 방식은 일반 모듈을 그대로 쓸 수 있지만 마지막 모듈만 길이가 달라 이음새가 보일 수 있습니다. 대각선 벽이 있으면 벽끼리 만나는 각도가 90도, 45도, 63도처럼 제각각이라 수·각도별 코너 프리팹은 종류가 많아집니다. 같은 기둥을 놓는 방식은 각도와 상관없이 이음새를 가릴 수 있습니다. 벽 높이는 5단계 Q327, 벽마다 다른 프리팹은 6단계 Q354에서 묻습니다.

답:0.25 유닛짜리 벽 모듈+모든 노드에 기둥

Q460. [핵심] 노드 시스템에 넣을 기물과 문·레이저 벽의 형태

3단계 Q326에서 벽으로 취급할 수 있는 기물(문 등)은 노드 시스템에 넣고, 그 밖의 기물은 설치형으로 하기로 했습니다. 문은 이 답에 이미 들어 있으므로, 문 말고 노드 시스템에 넣을 기물과, 문·레이저 벽을 노드 데이터에서 어떻게 나타낼지 정해야 합니다. 5단계 Q329(문 개구부 처리)는 이 질문으로 합쳤습니다.

  [문 말고 노드 시스템에 넣을 기물] (여러 개 골라도 됨)
    - 레이저 벽
    - 없음 (문만)
    - 기타
  [문의 형태]
    - 노드 사이 구간 하나가 통째로 문 (문 양쪽 끝에 노드를 둠)
    - 벽 구간 중간에 정해진 폭의 문을 끼움 (구간 위의 위치만 지정하고, 그 자리의 벽은 자동으로 비움)
    - 기타
  [레이저 벽의 형태] (노드 시스템에 넣을 때)
    - 노드 사이 구간 하나
    - 이어진 여러 구간을 묶어 레이저 벽 하나로 다룸 (작동기 하나로 함께 꺼짐)
    - 기타

나머지 기물(작동기, 합성기, 추출 오브젝트, 목적지, 체크포인트)은 설치형으로 읽었습니다. 다르면 첫 항목의 '기타'에 적어 주세요. 구간 하나를 통째로 문으로 쓰면 문 폭이 노드 사이 거리가 되어, 대각선 구간이면 정수가 아닐 수 있습니다(문 프리팹을 늘려야 함). 정해진 폭으로 끼우면 문 프리팹은 하나로 되지만 끼울 위치를 정하는 편집 기능이 필요합니다. 레이저 벽은 여러 칸을 차지하는 문이고(1차 Q27) 콜라이더는 레이저 벽 전체를 MeshCollider 하나로 만들기로 했으므로(2단계 Q261), 묶는 방식이면 묶인 구간 전체가 콜라이더 하나가 됩니다. 문과 레이저 벽을 언제 오브젝트로 만들지는 이 파일의 Q458에서 묻습니다.

답:문과 유사한 작동은 노드 시스템, 벽 구간 사이에 문 설치, 노드 사이 구간 하나

Q461. [보통] 바라볼 때 뜨는 값 표시의 조건·대상·위치

3단계 Q454에서 오브젝트를 바라보면 그 값이 공중에 떠서 보이게 했고, Q224에서는 맵 위에 라벨을 붙이지 않기로 했습니다. 두 답을 함께 읽으면 '늘 붙어 있는 라벨은 없고, 바라볼 때만 값이 뜬다'입니다. 이 표시가 뜨는 조건과 대상, 위치를 정해야 합니다.

  [뜨는 조건]
    - 조준점이 오브젝트에 닿고 상호작용 거리 안일 때 (추출·제출할 수 있는 거리와 같음)
    - 조준점이 오브젝트에 닿으면 거리와 상관없이
    - 기타
  [대상] (여러 개 골라도 됨)
    - 추출 오브젝트 (추출 전)
    - 문·목적지·작동기 (요구 값)
    - 기타
  [표시 위치]
    - 오브젝트 위 공중 (월드 공간, 오브젝트를 따라감)
    - 화면의 조준점 옆 (화면 공간)
    - 기타

상호작용 거리는 모든 상호작용에 같은 값을 쓰고 구체 값은 개발하면서 정합니다(2단계 Q175). v1에는 조준 대상이 바뀔 때 강조 표시를 바꾸고 InteractableTargetChanged 이벤트를 보내는 코드가 있어서, 값 표시도 같은 조준 판정에 붙일 수 있습니다. 문·목적지·작동기를 대상에 넣으면 팝업을 열지 않고도 요구 값을 볼 수 있습니다(3단계 Q224의 'UI에 값 표시'와 함께 쓰는 것). 추출한(무채색으로 바뀐) 오브젝트를 바라볼 때 무엇을 보일지는 5단계 Q370, 숫자 형식은 5단계 Q403에서 묻습니다.
참고 코드: Assets/Scripts/Player/InteractionController.cs

답:조준점이 오브젝트에 닿고 상호작용 거리 안일 때,값을 확인할수 있는 모든 대상, 화면 공간

Q463. [보통] 첫 로드 팝업 시스템의 범위

  [뜨는 때] (여러 개 골라도 됨)
    - 게임을 처음 실행할 때 한 번 (공통 안내)
    - 맵마다 처음 들어갈 때 (맵마다 다른 내용, 내용이 없는 맵은 안 뜸)
    - 새 기물을 처음 만났을 때 (합성기, 문, 레이저 벽 등을 처음 볼 때)
    - 기타

    - 다시 볼 수 없음
    - 기타
  [한 번 본 팝업]
    - 기록해서 다시 띄우지 않음
    - 들어갈 때마다 띄움 (닫기 버튼으로 넘김)
    - 기타
