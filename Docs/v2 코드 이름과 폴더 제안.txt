ColorMaze v2 코드 이름과 폴더 제안
============================================================

작성일: 2026-10-28
기준 문서: Docs/v2 코드 흐름 설계.md (2026-10-28 동의), Docs/v2 결정 로그.md, Docs/v2 기물 분류.md

이 파일의 범위: 코드 흐름 설계에 동의한 뒤 정하기로 한 코드 이름, 폴더 이름, 매핑 테이블입니다(3차 Q486). 코드 흐름 문서에 한글로 적은 클래스·인터페이스·이벤트·애셋마다 코드 이름을 붙이고, 스크립트·애셋을 둘 폴더를 정합니다.
이 파일의 질문 수: 11개 (Q505~Q515)

[작성 방법]

  - 각 질문의 "답:" 뒤에 자유롭게 적어 주세요. 선택지는 예시일 뿐이며 선택지에 없는 답도 괜찮습니다.
  - 이름 목록(Q508~Q512)은 "제안대로"라고 적거나, 바꿀 이름만 "한글 이름: 원하는 이름"으로 적으면 됩니다.
  - 질문 번호는 코드 흐름 설계의 마지막 선택(Q504)에 이어 Q505부터 붙였습니다. 결정 로그에는 "(코드 이름 Q505)"처럼 인용하겠습니다.
  - 기획 문서의 한글 이름(문, 작동기, 목적지 등)은 그대로 쓰고, 여기서 정하는 것은 코드에서 쓰는 영어 이름입니다.
  - 이름 목록은 Q505~Q507의 참고 의견대로 지었습니다. 규칙을 다르게 고르면 목록도 그 규칙에 맞춰 고치겠습니다.
  - Q509~Q515의 제안은 Q505~Q508의 답에 맞춰 2026-10-28에 고쳤습니다: 설정 애셋은 끝에 Config, v1 코드를 먼저 지우고 v2 코드를 씀(v1 이름도 쓸 수 있음), 어셈블리는 ColorMaze.Assembly, Q508의 계열·종류 이름. 기물의 계열과 종류는 Docs/v2 기물 분류 편집기.html로 고치는 중이라, Q513의 계열 폴더는 그 결과를 따릅니다.
  - "참고 의견"은 제 추천이고 따르지 않아도 됩니다.

Q505. [핵심] 이름을 짓는 규칙

[이미 정해진 전제]
  - v2 새 코드는 ColorMaze 네임스페이스에 둡니다. (3차 Q489)
  - 이미 정한 코드 이름: OrbValue(오브 값), SubmittableObjectBase(작동기 계열의 공통 기본 클래스). (2차 Q101, Q263)
  - 지금 코드는 영어 PascalCase 클래스이고 파일 이름이 클래스 이름과 같습니다. 추상 기본 클래스는 Base로 끝나고(MapObjectBase, FilterBlockBase), 이벤트는 '대상 + 일어난 일'(SceneLoadCompleted, ColorStackChanged)이며 Event를 붙이지 않습니다.
  - 겉모습(문짝 움직임, 강조, 색 표시)은 로직과 나눈 별도 컴포넌트입니다. (코드 흐름 1절)

[빈 곳]
  v2 코드 전체에 같은 규칙을 쓰려면 규칙을 먼저 정해야 합니다.

  [클래스와 파일]
    - 영어 PascalCase, 파일 이름 = 클래스 이름 (지금 코드와 같음)
    - 기타
  [추상 기본 클래스]
    - 끝에 Base (지금 코드와 같음: SubmittableObjectBase, GateBase)
    - 앞에 Abstract (AbstractGate)
    - 붙이지 않음 (Gate)
  [인터페이스]
    - 앞에 I (IInteractTarget)
    - 기타
  [이벤트]
    - '대상 + 일어난 일', Event를 붙이지 않음 (OrbExtracted, GateStateChanged — 지금 코드와 같음)
    - 끝에 Event (OrbExtractedEvent)
  [겉모습 컴포넌트]
    - 끝에 View (DoorView, LinkColorView)
    - 끝에 Visual (DoorVisual)
    - 붙이지 않음
  [설정 애셋 (ScriptableObject)]
    - 내용을 나타내는 이름 (GameRules, NodeBuildSettings, LinkColorPalette, SoundTable)
    - 모두 끝에 Config (GameRulesConfig, NodeBuildConfig ...)
  [v1에 이미 있는 이름]
    - 피함 (v1 MapObjectBase, IInteractable, InteractionController와 다른 이름을 쓰고, v1을 지운 뒤에도 그대로 둠)
    - 같은 이름을 씀 (네임스페이스로 나뉘어 컴파일은 됨)
    - 같이 있는 동안만 피하고, 0.0.1 때 v1을 지우면서 v1 이름으로 바꿈

Base와 I는 지금 코드와 C# 관례에 맞습니다. 이벤트에 Event를 붙이면 이벤트라는 것은 잘 보이지만 지금 코드의 이벤트(SceneLoadCompleted 등)와 모양이 달라집니다. 겉모습 컴포넌트에 View를 붙이면 '이 컴포넌트는 그리기만 한다'가 이름으로 드러나 로직을 넣지 않게 됩니다. v1과 같은 이름은 네임스페이스로 나뉘어 컴파일은 되지만, 같이 있는 동안 검색과 인스펙터의 컴포넌트 목록에서 헷갈립니다. 0.0.1 때 v1 이름으로 바꾸면 이름은 짧아지지만 그때 v2 코드 전체의 이름을 한 번 더 바꿔야 합니다.

[참고 의견]
  - 영어 PascalCase + 파일 이름 = 클래스 이름 / Base / I / Event를 붙이지 않음 / View / 내용을 나타내는 이름 / v1과 같은 이름은 피함.

답:영어 PascalCase + 파일 이름 = 클래스 이름 / Base / I / Event를 붙이지 않음 / View / Config / v1을 지우면서 코드 생성

Q506. [보통] 기물 공통 기반의 이름

[이미 정해진 전제]
  - 모든 v2 기물이 상속하는 기반입니다. 맵 안 id, 맵 매니저 등록, 상호작용 강조, 상태 저장 기본 구현을 맡습니다. (코드 흐름 6.1)
  - v1에는 같은 역할의 MapObjectBase가 있고 0.0.1 때 지웁니다. v1 맵 에디터(UGC)의 데이터는 기물을 Fixture라고 부릅니다(FixtureType, FixtureEntry). (2차 Q414)

[빈 곳]
  기물이라는 말에 맞는 영어 이름을 정합니다. 이 이름은 맵 안 id(FixtureId), 스냅샷의 기물 상태 항목, 에디터 검사, 나중에 고칠 UGC 데이터 이름에도 이어집니다.

  [이름]
    - FixtureBase (기물 = Fixture, v1 맵 에디터와 같은 말)
    - MapElementBase (기물 = Map Element)
    - PuzzleObjectBase
    - 기타

Fixture는 '자리에 설치된 장치'라는 뜻이라 문·작동기·합성기 같은 기물에 맞고, UGC 데이터를 v2로 고칠 때 FixtureEntry 같은 이름을 그대로 이어 쓸 수 있습니다. MapElement는 더 넓은 말이라 벽과 노드까지 포함하는 것처럼 읽힙니다. PuzzleObject는 뜻은 분명하지만 길고 v1 MapObjectBase와 모양이 비슷합니다.

[참고 의견]
  - FixtureBase. 아래 목록(Q508~Q512)은 이 이름으로 적었습니다.

답:FixtureBase

Q507. [보통] 네임스페이스와 어셈블리 이름

[이미 정해진 전제]
  - v2 새 코드는 ColorMaze 네임스페이스에 둡니다. (3차 Q489)
  - 코어 규칙만 asmdef 하나로 묶고, EditMode 테스트용 asmdef를 따로 둡니다. 월드와 UI는 기본 어셈블리(Assembly-CSharp)에 둡니다. (3차 Q489, 코드 흐름 2절)

[빈 곳]
  [네임스페이스]
    - ColorMaze 하나 (하위 네임스페이스 없음)
    - 역할별 하위 네임스페이스 (ColorMaze.Rules, ColorMaze.Fixtures, ColorMaze.UI 등)
    - 기타
  [에디터 전용 코드]
    - 같은 ColorMaze 네임스페이스 (Editor 폴더에 있어 빌드에서 빠짐)
    - ColorMaze.EditorTools
  [어셈블리 이름]
    - 코어 규칙 ColorMaze.Rules / 테스트 ColorMaze.Rules.Tests
    - 코어 규칙 ColorMaze.Core / 테스트 ColorMaze.Core.Tests
    - 기타

하위 네임스페이스는 큰 프로젝트에서 이름이 부딪치는 것을 막지만 파일마다 using이 늘고, 1인 프로젝트 규모에서는 폴더만으로 충분히 나뉩니다. 에디터 코드에 ColorMaze.Editor라는 네임스페이스를 쓰면 유니티의 Editor 클래스와 이름이 부딪쳐 오류가 나기 쉬우므로, 나누려면 EditorTools처럼 다른 이름이 필요합니다. 어셈블리를 Core라고 부르면 지금의 Assets/Scripts/Core 폴더(GameManager 등, 기본 어셈블리)와 헷갈립니다.

[참고 의견]
  - ColorMaze 하나 / 에디터 코드도 같은 네임스페이스 / ColorMaze.Rules, ColorMaze.Rules.Tests.

답:ColorMaze 하나 / 에디터 코드도 같은 네임스페이스 / ColorMaze.Assembly, ColorMaze.Assembly.Tests

Q508. [핵심] 기물 계열과 종류 (매핑 테이블에 들어갈 것)

[이미 정해진 전제]
  - 기물의 계열과 종류는 Docs/v2 기물 분류.md가 단일 출처이고, 한글 이름은 임시 용어입니다. 기획 용어와 코드 이름은 매핑 테이블로 잇습니다. (2차 Q265, 3차 Q486)
  - 작동기 계열의 공통 기본 클래스는 SubmittableObjectBase로 정했습니다. (2차 Q263)

[빈 곳]
  계열 이름은 폴더 이름(Q513)과 기반 클래스 이름에도 쓰입니다.

  [계열]
    - 문 계열 → Gate (기반 GateBase)
    - 작동기 계열 → Submittable (기반 SubmittableObjectBase, 이미 정함)
    - 오브 획득 계열 → OrbSource
    - 기타 기믹 계열 → Gimmick
    - 출발점 계열 → SpawnPoint (기반 SpawnPointBase)
  [종류]
    - 문 → Door
    - 레이저 벽 → LaserWall
    - 일회용 작동기 → OneShotActuator
    - 반복 작동기 → ReusableActuator
    - 목적지 → Goal
    - 추출 오브젝트 → ExtractableObject
    - 합성기 → Synthesizer
    - 시작 지점 → StartPoint
    - 체크포인트 → Checkpoint
  [계열 안의 중간 기반]
    - 작동기 기반 (일회용·반복 작동기의 공통: 작동 대상 1개, 연결색) → ActuatorBase

Gate는 '통로를 막고 여는 것'이라 문과 레이저 벽을 함께 부르기 좋습니다. 작동기 계열에는 목적지도 들어 있어서, 계열 이름은 이미 정한 SubmittableObjectBase(오브를 제출받는 것)에 맞춰 Submittable로 했고, 문 계열을 여닫는 일회용·반복 작동기만 ActuatorBase를 거칩니다. 반복 작동기는 OneShot(한 번)과 짝을 이루는 Reusable(다시 쓸 수 있음)로 했고 Repeatable도 됩니다. 목적지는 오브를 내서 클리어하는 곳이라 Goal로 했고 Exit나 Destination도 됩니다. 출발점 계열은 플레이어가 나타나는 곳이라 SpawnPoint로 했습니다.

[참고 의견]
  - 제안대로.

답:오브 획득 계열 -> ColorSource ( 색상 오브의 획득처 의미)
기타 기믹 계열은 추가하라는게 아니라 나중에 다른 계열들을 추가할수 있다는 의미
계단 계열 -> FloorMove (기반 FloorMoveBase)
일회용 작동기 -> SingleUseActuator
추출 오브젝트는 여러 종류의 사물들이 들어올 예정이라 해당 사물의 이름을 사용
합성기 -> ColorMixer

Q509. [보통] 코어 규칙

[이미 정해진 전제]
  - 코어 규칙은 순수 C#이고 asmdef 하나로 묶습니다. 오브 값, 오브 규칙, 소지 오브, 합성·제출 세션, 작동기 상태, 팝업 호스트 인터페이스, 스냅샷 데이터, 노드 데이터가 들어갑니다. (코드 흐름 4절)

[빈 곳]
  [오브]
    - 오브 값 → OrbValue (이미 정함)
    - 오브 규칙 (한도, 목표·추출 값 규칙, 색 변환) → OrbRules
    - 소지 오브 → OrbInventory
    - 소지 오브 항목 (런타임 번호 + 값) → HeldOrb
  [세션]
    - 합성 세션 → SynthesisSession
    - 제출 세션 → SubmitSession
    - 작동기 종류 (일회용 / 반복 / 목적지) → SubmitKind { SingleUse, Reusable, Goal }
    - 제출 결과 → SubmitOutcome
    - 거부 이유 (값이 다름 / 슬롯이 참 / 소지 오브가 가득 참) → SubmitRejectReason { WrongValue, SlotOccupied, InventoryFull }
    - 작동기 상태 → ActuatorState
  [팝업과 ESC]
    - 팝업 호스트 인터페이스 → IPopupHost
    - 팝업 정적 접근점 → Popups (기물은 Popups.Open(세션, 닫힐 때 할 일)로 부름)
    - 뒤로 가기 스택 → BackStack
  [저장과 노드 데이터]
    - 맵 스냅샷 → MapSnapshot
    - 기물 상태 항목 (맵 안 id + JSON 문자열) → FixtureStateEntry
    - 노드 그래프 데이터 (노드·벽 목록, 다음 id) → NodeGraphData
    - 노드 / 벽 / 끼운 문 항목 → NodeData / WallData / DoorData
    - 벽 종류 → WallKind { Normal, Laser }
    - 노드 계산 (id 발급, 합치기, 모듈 수, 문 끼우기 가능 여부) → NodeGraphRules
  [테스트]
    - 테스트 클래스 → 대상 이름 + Tests (OrbValueTests, SubmitSessionTests 등)

세션은 '팝업 한 번 동안의 상태'라 Session으로 했습니다. 소지 오브 항목은 슬롯(칸 수)과 헷갈리지 않게 '들고 있는 오브'라는 뜻의 HeldOrb로 했습니다. 뒤로 가기 스택은 일시정지 메뉴(기본 어셈블리)와 팝업 호스트가 함께 쓰는 순수 C#이라 코어 규칙에 둡니다. 작동기 종류의 값은 Q508의 일회용 작동기 이름(SingleUseActuator)에 맞춰 SingleUse로 했습니다.

[참고 의견]
  - 제안대로.

답:추천대로 (2026-10-28 채팅). 반영할 때 합성 쪽 이름은 합성기 ColorMixer에 맞춰 MixSession으로 통일(채팅)

Q510. [보통] 맵 · 기물 공통 · 플레이어 · 노드 시스템

[이미 정해진 전제]
  - 맵 매니저는 맵 씬마다 하나입니다. 기물은 공통 기반과 인터페이스 넷(상호작용, 값 제공, 상태 저장, 작동 대상)을 씁니다. (코드 흐름 3.3, 6.1)
  - 노드 시스템은 모양(노드 쪽 상속)과 문 계열의 동작(별도 컴포넌트)을 나눕니다. 끼운 문과 레이저 벽은 두 컴포넌트를 같은 오브젝트에 붙입니다. (코드 흐름 11.4)

[빈 곳]
  [맵]
    - 맵 매니저 → MapManager
    - 맵 씬 기본 프리팹 → MapRoot (프리팹)
    - 맵 안 id (기물의 필드) → FixtureId
  [기물 공통]
