## 0. 이 문서에 대해

- **범위**: 코어 루프(결정 로그 9절, 3차 Q490)를 자세히 쓴다. 체크포인트·저장·이어하기·'처음부터'·메뉴 흐름은 코어 루프 뒤에 만들지만, 그때 코어 루프 코드를 고치지 않도록 **들어갈 자리**만 정한다.
- **수준**: 무엇이 무엇을 맡는지, 누가 누구를 부르는지, 어떤 데이터와 이벤트가 오가는지까지 쓴다. 함수는 대표적인 것만 적는다.
- **이름**: 새로 만드는 것은 역할을 나타내는 한글 이름(예: 맵 매니저, 소지 오브, 제출 세션)으로 쓴다. 이미 정한 코드 이름(`OrbValue`, `SubmittableObjectBase`)과 지금 있는 클래스 이름(`GameManager`, `InputManager` 등)은 그대로 쓴다. 코드 이름은 처음 나오는 곳(절 제목, 표)에 한글 이름 옆에 적는다(예: 맵 매니저(`MapManager`), 코드 이름 Q515). 이름 규칙은 결정 로그 10절에 있다.
- **[제안]**: 여러 방법 중 하나를 고른 곳이다. 고른 방법과 다른 방법을 함께 적고, 15절에 번호(Q493~)를 붙여 모았다. 결정 로그에는 '(코드 흐름 Q###)'로 인용한다. 2026-10-28에 모두 제안대로 정해졌다.

## 1. 설계 기준

세 목표를 코드 규칙으로 옮겼다.

- **확장성**: 새 기물·팝업·노드 종류를 더할 때 **기반 클래스를 상속하거나 인터페이스를 구현하고 프리팹을 만드는 것**으로 끝나게 한다. 맵 매니저, 조준, 저장, UI는 기물의 종류를 몰라도 동작한다.
- **유지보수**: **규칙**(무엇이 맞는가), **겉모습**(어떻게 보이는가), **연결**(누가 누구에게 알리는가)을 나눈다. 하나의 결정은 한 곳에서만 바뀐다(판정은 코어 규칙, 수치는 설정 애셋, 소리는 소리 연결, 색은 연결색 목록).
- **개발 편의**: 규칙은 Play 없이 EditMode 테스트로 확인한다. 맵 씬은 Play 한 번으로 바로 시험한다. 맵 실수는 에디터 검사가 먼저 잡는다. 수치는 인스펙터에서 바꾼다.

규칙

1. **의존은 한 방향이다.** 월드(기물·플레이어·맵)와 UI는 코어 규칙에 기대고, 코어 규칙은 아무것도 모른다. 월드는 UI 클래스를 모르고, 둘은 이벤트와 인터페이스로만 만난다.
2. **규칙은 순수 C#이다.** MonoBehaviour가 아니고 씬 없이 만들 수 있어 테스트할 수 있다.
3. **기물 컴포넌트는 세 가지만 한다.** 입력을 받아 규칙을 부르고, 상태를 바꾸고, 이벤트를 보내거나 겉모습에 알린다.
4. **겉모습은 따로 둔다.** 문짝 움직임, 레이저 오르내림, 강조, 색 표시는 별도 컴포넌트다. 로직은 상태만 알리므로 아트를 바꿔도 로직은 그대로다.
5. **같은 씬 안의 연결은 인스펙터 참조**, 씬을 넘는 연결(맵 씬 ↔ UIScene)은 EventBus나 등록식 접근점으로 한다.
6. **전역 싱글톤은 늘리지 않는다.** 지금 있는 전역 서비스만 쓰고, 맵 범위의 것은 맵 씬마다 있는 맵 매니저를 거친다.
7. **수치는 설정 애셋 한 곳**에 둔다.
8. **맵 설계 규칙 중 기계로 확인할 수 있는 것은 에디터 검사**가 잡는다.

- **어셈블리**: 코어 규칙만 asmdef 하나로 묶고(테스트용 asmdef 하나 더), 월드와 UI는 기본 어셈블리(Assembly-CSharp)에 둔다. asmdef로 묶은 코드는 기본 어셈블리를 참조할 수 없으므로, 월드·UI까지 묶으면 `GameManager`, `InputManager` 같은 지금 코드를 쓸 수 없다. 반대로 기본 어셈블리는 asmdef를 자동으로 참조하므로 월드·UI에서 코어 규칙을 바로 쓴다. 이 구조 덕분에 규칙 1(코어 규칙은 아무것도 모름)은 컴파일러가 지켜 준다.
- 코어 규칙은 UnityEngine의 값 타입(`Color`, `Vector3`)은 써도 되지만 MonoBehaviour와 씬 오브젝트는 쓰지 않는다.
- 새 코드는 모두 `ColorMaze` 네임스페이스 하나에 둔다(3차 Q489, 코드 이름 Q507). 어셈블리 이름은 코어 규칙 `ColorMaze.Assembly`, 테스트 `ColorMaze.Assembly.Tests`다. v1 코드는 v2 코드를 쓰기 전에 지우므로(14절 0단계) v1 이름과 겹칠 일이 없다.

## 3. 씬과 수명

### 3.1 씬 구성

- **부팅 씬**(`Boot`, 새로 만듦)에서 `Bootstrap`이 전역 서비스를 깨우고 다음 씬을 불러온다(코어 루프 동안은 시험 씬, 메뉴 흐름을 만들 때 메인 메뉴로 바꿈). 맵 씬은 `SceneLoader`로 불러오며, UIScene은 `UIManager`가 늘 additive로 얹는다(2차 Q288).
- **맵 씬**에는 맵 매니저(`MapManager`) 1개, 플레이어(`Player` 프리팹) 1개, 시작 지점(`StartPoint`) 1개, 노드 그래프(`NodeGraph`) 1개(벽·문·레이저 벽), 설치형 기물이 있다.
- **맵 씬 기본 프리팹**(`MapRoot`): 맵 매니저 + 플레이어 + 노드 그래프 루트를 하나로 묶어, 새 맵은 이 프리팹을 끌어다 놓고 시작한다(설정 애셋 연결도 프리팹에 들어 있음).

### 3.3 맵 매니저의 수명

- 맵 씬마다 하나 있고 씬과 함께 생기고 사라진다(DontDestroyOnLoad가 아님). v1 `LevelManager`처럼 씬이 바뀔 때마다 목록을 다시 모으는 일이 없다.
- '지금 맵'을 정적 접근점 하나로 내놓는다(Awake에서 설정, OnDestroy에서 해제). 맵 범위의 것을 찾는 길은 이것 하나다.
- 기물보다 먼저 깨어나도록 실행 순서를 앞에 둔다. 기물은 OnEnable에서 등록하고 OnDisable에서 해제한다.
- 시작할 때: 상태가 Playing이 아니면 Playing으로 맞추고(열린 맵에서 바로 시작한 경우), 플레이어를 시작 지점으로 옮기고, 클리어 시간을 0으로 두고, '맵 시작' 이벤트를 보낸다. 2단계에서는 앞의 둘만 만들었다. 클리어 시간은 7단계에서 더했고(맵 씬과 함께 새로 생기므로 0부터, 10.1), '맵 시작' 이벤트는 받는 곳이 생길 때 더한다(2차 Q267).

### 3.4 열린 맵에서 바로 시작 (`DirectPlayLoader`) [제안 Q495]

- v1의 에디터 스크립트 `PlayFromMainMenu`는 Play를 누르면 늘 MainMenu부터 시작했다. v2에서는 Play를 늘 부팅 씬(`Boot`)부터 시작하고, 3차 Q490의 '시험 씬을 에디터에서 바로 열어 확인'을 위해 예외를 둔다.
- **제안**: 에디터 메뉴에 켜고 끄는 항목 'Play: 열린 맵에서 바로 시작'을 둔다(켜짐 여부는 EditorPrefs에 기억). 켜져 있고 열린 씬이 부팅 씬이 아니면, Play를 눌렀을 때 부팅 씬에서 평소처럼 부팅한 뒤 **열려 있던 씬을 바로 불러온다**(에디터 전용 코드). 부팅 순서를 그대로 쓰므로 부팅 씬에만 있는 설정(`GameAudio`의 클립 연결 등)이 빠지지 않는다. Build Settings에 없는 씬도 에디터에서는 경로로 불러온다.
- 다른 방법: 부팅 오브젝트를 프리팹으로 묶어 맵 씬에서도 부팅한다. 부팅 경로가 둘이 되어 고칠 곳이 늘어난다.
- 바로 시작은 디스크의 씬을 불러오므로, 켜져 있을 때 Play를 누르면 고친 씬을 먼저 저장할지 묻는다(취소하면 Play도 취소, 2단계 구현).

## 4. 코어 규칙 (순수 C#)

### 4.1 OrbValue

- `OrbValue { int r, g, b }` 구조체(2차 Q101). 덧셈, `==`/`!=`, 가장 큰 채널, 'R G B' 문자열(예: `2 0 0`). 빼기와 배수는 필터·증폭기를 만들 때 더한다.
- 인스펙터에 보이도록 직렬화 필드를 두지만 코드에서는 값으로만 다룬다(바꿀 때는 새 값을 만듦).
- 채널 한도도 채널마다 따로인 세 정수라 이 타입으로 나타낸다(1단계 구현).

### 4.2 오브 규칙 (`OrbRules`)

채널 한도는 **채널마다 따로인 값**(기본 (5,5,5), 흡수로 늘어남, 결정 로그 1절)으로 인자로 받는다. 그래서 테스트에서는 아무 값이나 넣을 수 있다.

- **한도 안인가**: 모든 채널이 0~그 채널의 한도.
- **자르기**: 채널마다 0~그 채널의 한도로 자른다(음수는 0, 넘치면 한도). 합성·필터·증폭기의 결과는 모두 이것을 거친다(결정 로그 1절). 그래서 오브는 늘 한도 안이고, (0,0,0) 오브도 있을 수 있다(필터 결과).
- **목표로 쓸 수 있는가**: 모든 채널 1 이상, 세 채널이 모두 같지 않음(2차 Q373, Q455). 기본 한도를 넘어도 된다(상한은 미정, 결정 로그 1절). 에디터 검사가 쓴다.
- **추출 오브젝트 값으로 쓸 수 있는가**: (0,0,0)과 세 채널이 같은 값이 아님(2차 Q455).
- **색**: 가장 큰 채널로 나눈 정규화 RGB(오브는 늘 최대 밝기, 2차 Q262). **발광 세기**는 가장 큰 채널에 비례(계수는 설정 애셋, 2차 Q412). **흑백 변환**은 채도만 0(밝기 계산 방식은 구현 때, 2차 Q170). 흑백 변환은 처음 쓰는 곳이 생길 때 더하고, (0,0,0) 오브의 색은 모양이 미정이라 일단 검정으로 둔다(1단계 구현). 흑백 밝기는 **세 채널의 평균**이다(순수 빨강·초록·파랑이 같은 회색, 4단계, 4단계 구상 채팅).

### 4.3 소지 오브 (`OrbInventory`, 항목은 `HeldOrb`)

- 순서 있는 목록과 용량(슬롯 수). 오브 하나는 '소지 오브 항목'(런타임 번호 + `OrbValue`)이다. 같은 값이어도 번호로 구분한다(팝업에서 고르기, 흔들 대상).
- 더하기: 끝에 붙인다(들어온 순서, 2차 Q142). 가득 차면 실패한다. 빼기: 항목을 지정해 뺀다. 가득 찼는지, 개수, 읽기 전용 목록.
- 바뀌면 C# 이벤트 하나로 알린다.
- **채널 한도**: 지금 채널 한도(채널마다, 처음 값은 설정 애셋의 기본 한도)를 함께 든다. 합성 세션은 이 한도로 자른다.
- 상태 내보내기·불러오기: 값 목록(순서 그대로)과 채널 한도.
- 용량은 생성할 때 받는 값이다(나중의 '맵 안에서 슬롯을 늘리는 아이템'은 이 값을 바꾸는 것으로 끝나지만, 그 구조는 지금 만들지 않는다).
- **흡수**(`AbsorbSession`, 코어 루프 뒤): 인벤토리 창의 흡수 칸에 오브를 놓으면 그 항목을 빼고 채널 한도에 그 값을 더한다. 놓기 전, 흡수 칸 위에서 누르고 있는 동안에는 '바뀔 한도'를 미리 계산해 준다. 놓는 순간 적용한다(닫을 때 적용하는 합성·제출 세션과 다름, 결정 로그 1절).

### 4.4 합성 세션 (`MixSession`)

팝업 한 번 동안의 선택 상태다. 합성기는 오브를 보관하지 않으므로 닫으면 버린다(결정 로그 2절).

- **고르기/취소**: 모든 소지 오브를 고를 수 있다(한도를 넘어도 막지 않음, 결정 로그 1절 ← 2차 Q442의 회색 막기에서 바뀜). 같은 오브를 다시 누르면 취소.
- **미리보기**: 1개 이상 고르면 합을 자른 값(4.2).
- **합성**: 고른 항목을 빼고 자른 합을 끝에 더한다(재료가 빠지므로 늘 성공, 1개만 골라도 막지 않음, 2차 Q441). 선택을 비우고 결과를 돌려준다. 결과는 합성한 때 들어온 것이다.
- **닫기**: 선택을 버린다.
- (0,0,0) 재료는 합에 영향이 없어 다른 값을 바꾸지 않고 사라진다. 재료가 모두 (0,0,0)이면 결과도 더하지 않는다(결정 로그 1절, 1단계 구현).
- **오브 편집기 계열의 다른 종류**(필터·복제기·증폭기, 코어 루프 뒤): 지금은 합성 세션만 만든다. 두 번째 편집기를 만들 때 '재료 고르기 → 계산 → 결과'를 공통으로 묶을지 정한다(결정 로그 2절의 '필요해질 때 추가', 2차 Q129). 필터는 고른 순서가 결과를 바꾸고, 복제기는 빈 슬롯이 있어야 쓸 수 있다.
- 8단계 구현: 합성할 때 결과 값을 C# 이벤트(`Mixed`)로 알린다(합성기가 '합성함'으로 보냄). 결과가 (0,0,0)이어도 알린다.

### 4.5 제출 세션 (`SubmitSession`)

팝업 한 번 동안의 제출 상태다. 맞는지는 오브를 클릭할 때 판정하고, 결과는 닫을 때 작동기에 적용한다(결정 로그 4절 '제출 팝업의 흐름').

- **만들 때 받는 것**: 소지 오브, 판정 함수(작동기 계열 기반의 `TrySubmit`), 작동기 종류(`SubmitKind`: 일회용 / 반복 / 목적지), 열 때 제출 슬롯에 든 오브(반복 작동기만 있을 수 있음).
- **소지 오브 클릭(내기)**: 제출 슬롯이 비어 있고 판정이 맞으면, 소지 오브에서 빼서 슬롯으로 옮긴다(받아들임). 아니면 거부한다(흔들림). 슬롯이 차 있을 때 다른 오브를 누르면 거부한다 [제안 Q497].
- **슬롯 오브 클릭(되돌리기·회수)**: 반복 작동기이거나 이번 세션에 넣은 오브이고, 빼도 되고(작동기 계열 기반이 정함, 6.5 '플레이어 위로 닫히지 않게'), 소지 오브가 가득 차지 않았으면 소지 오브 끝으로 옮긴다(3차 Q480, 2차 Q469). 아니면 거부한다.
- **닫기**: 결과(`SubmitOutcome`: 슬롯에 든 오브, 없을 수 있음)를 돌려준다.
- 거부에는 이유(`SubmitRejectReason`: 값이 다름 / 슬롯이 참 / 소지 오브가 가득 참 / 닫힐 문 계열에 플레이어가 있음)를 붙인다. 지금은 모두 흔들림 하나지만 소리·연출을 나눌 때 쓴다.
- 6단계 구현: 제출 화면이 세션만 받으므로 요구 값(`Required`, 그리기용이고 판정은 그대로 판정 함수)과 소지 오브 목록(`Orbs`)을 더했다. 빼도 되는가는 함수(`canRelease`)로 받아 슬롯 오브를 누를 때 묻는다.
- 8단계 구현: 넣기·되돌리기·회수마다 받아들임 여부와 거부 이유를 C# 이벤트(`Attempted`)로 알린다(작동기 계열이 '제출 결과'로 보냄).

### 4.6 작동기 상태 (`ActuatorState`)

- 든 오브(없을 수 있음), 켜짐(= 든 오브가 있음), 다 씀(일회용 작동기가 켜진 뒤).
- **팝업을 열 수 있는가**: 다 쓴 일회용 작동기는 아님(3차 Q478), 클리어한 뒤의 목적지는 아님.
- 제출 세션의 결과를 받아 새 상태와 '켜짐이 바뀌었는가'를 돌려준다.

### 4.7 스냅샷 데이터 (`MapSnapshot`, 자리만, 체크포인트 단계에서 채움)

- 맵 스냅샷: 맵 id·맵 버전, 플레이어(위치·시선·소지 오브 값 목록·채널 한도), 기물 상태 목록(`FixtureStateEntry`: 맵 안 id + 상태), 맵 플레이 시간, 활성화된 체크포인트 id 목록(결정 로그 3절, 2차 Q450, 3차 Q488).
- **[제안 Q499]** 기물 상태는 **기물마다 자기 상태를 JSON 문자열로** 내보내고 스냅샷은 'id + 문자열' 목록으로 든다. 기물 종류가 늘어도 스냅샷 형식은 그대로다(JsonUtility는 여러 타입이 섞인 목록을 못 담음).
  - 다른 방법: 종류별 필드를 모은 큰 상태 클래스. 기물 종류가 늘 때마다 형식을 고쳐야 한다.

### 4.8 노드 데이터 (`NodeGraphData`, `NodeData`, `WallData`, `DoorData`, `WallKind`, 계산은 `NodeGraphRules`)

- 노드·벽·끼운 문 항목 클래스(11.1). 유니티 에디터 맵의 노드 그래프와 UGC의 `CustomStageData`가 **같은 클래스**를 쓴다(2차 Q321).
- id는 노드·벽·끼운 문이 노드 그래프의 다음 id 하나를 함께 쓴다. 끼운 문의 위치는 구간의 첫 벽 모듈부터 센 모듈 수(문의 시작 쪽 가장자리)이고, 문 설정은 6단계에서 더한다. 문 폭은 임시값이라 계산 함수가 인자로 받는다(1단계 구현).
- 순수 계산: id 발급(맵 안에서 1부터 늘어나는 정수, 지운 번호는 다시 쓰지 않음, 2차 Q340), 같은 자리 노드 합치기(2차 Q352), 구간 길이로 모듈 수와 남는 길이 계산(2차 Q459), 문을 끼울 수 있는지(양옆에 문 폭 절반만큼 벽, 그림 0).
- 3단계에서 더한 계산: 편집(노드 더하기 — 같은 자리면 그 노드, 노드 지우기 — 붙은 벽도, 벽 잇기 — 같은 노드·높이가 다른 노드·이미 이어진 두 노드는 거부, 벽 지우기), 모양(첫 모듈 위치 — 남는 길이를 양 끝에 반씩, 콜라이더 구간, 문을 끼울 수 있는 위치의 범위, 바닥·천장 판). 합치기는 같은 두 노드를 잇게 된 벽을 하나만 남긴다.

### 4.9 EditMode 테스트 목록

테스트 클래스 이름은 대상 이름 + `Tests`다(예: `OrbValueTests`, `SubmitSessionTests`, 코드 이름 Q509).

| 대상 | 확인할 것 |
|---|---|
| OrbValue·오브 규칙 | 덧셈, 같음 비교, 한도, 자르기(음수는 0, 넘치면 한도), 목표·추출 값 규칙, (1,0,0)과 (2,0,0)이 같은 색 |
| 소지 오브 | 들어온 순서, 가득 참, 뺀 뒤 순서 |
| 합성 세션 | 한도를 넘는 합이 잘림, 1개 합성, 결과가 끝에 들어감, 닫으면 선택 초기화, 합성하면 결과 값을 알림(8단계) |
| 제출 세션 | 맞음·틀림, 슬롯이 찼을 때, 닫기 전 되돌리기(일회용·목적지), 반복 작동기 회수, 소지 오브가 가득 차 회수 불가, 닫을 때 결과, 넣기·회수마다 결과를 알림(8단계) |
| 작동기 상태 | 일회용은 켜지면 다 씀, 반복은 켜짐·꺼짐, 팝업을 열 수 있는가 |
| 스냅샷 데이터 | 소지 오브·기물 상태를 내보내고 불러오면 같음 |
| 노드 데이터 | id 발급, 노드·벽 편집, 합치기(겹친 벽 정리 포함), 모듈 수와 첫 모듈 위치, 문을 끼울 수 있는 범위, 콜라이더 구간, 바닥·천장 판(아래층 천장과 위층 바닥이 한 판) |

## 5. 플레이어

### 5.1 플레이어 프리팹 (`Player`)

v1 `Player` 프리팹은 0단계에서 지우고(14절) 같은 이름으로 새로 만든다(코드 이름 Q510). 이동 컴포넌트도 v1을 참고해 새로 쓴다.

| 부분 | 맡는 것 |
|---|---|
| 이동 (`FirstPersonController`) | v1 `FirstPersonController`를 참고해 새로 쓴다. 게임플레이 입력이 잠겨 있으면 이동·회전하지 않는다. 수치는 v1 값에서 시작해 조정(2차 Q211, Q212). 피벗은 발밑(CharacterController 중심 높이 0.8)이라 시작 지점 위치로 바로 옮기고, 카메라 눈높이는 1.3이다(2단계 구현). |
| 조준 컨트롤러 (`InteractionController`, 새로) | 매 프레임 상호작용 거리만큼 화면 중앙으로 레이캐스트해 조준 대상을 고른다. 보일 값이 바뀌면 '조준 대상 바뀜'을 보낸다. 좌클릭이면 대상과 상호작용한다. 입력이 잠겨 있거나 일시정지 중이면 아무것도 안 한다. |
| 소지 오브 컴포넌트 (`PlayerInventory`) | 코어 규칙의 소지 오브를 들고(용량과 기본 채널 한도는 설정 애셋), 바뀌면 '소지 오브 바뀜'을 보낸다. Tab을 받아 인벤토리 창을 연다(7.7). |
| 뷰모델 (`OrbViewmodel`) | '소지 오브 바뀜'을 받아 오른손 위의 구를 다시 그린다(색은 정규화 RGB, 발광은 가장 큰 채널에 비례). '추출함'을 받아 손을 뻗는 연출을 한다(손은 임시 모양). |

- 4단계 구현
  - 조준 컨트롤러는 맞은 콜라이더의 부모에서 기물 기반을 찾고, 상호작용할 수 있으면 좌클릭으로 상호작용한다. '조준 대상 바뀜'은 받는 곳(조준 값 표시)을 만드는 8단계에서 더한다. 뷰모델에는 콜라이더가 없어 레이캐스트에 걸리지 않는다.
- 8단계 구현
  - 조준 컨트롤러는 상호작용할 수 없는 대상도 값 제공으로 값을 읽고, (보일 값이 있는가, 값)이 바뀔 때만 '조준 대상 바뀜'을 보낸다(값을 보이는 쪽만 받으므로 같은 값의 다른 대상으로 옮겨도 보내지 않음). 입력이 잠기거나 일시정지면 대상이 비므로 팝업·일시정지·클리어 화면에서 값 표시가 숨는다.
  - 소지 오브 컴포넌트가 Tab으로 인벤토리 창을 열고 닫는다(열려 있으면 `Popups.Close`). `Time.timeScale`이 0이면(일시정지·클리어 화면) 열지 않고, 다른 팝업이 열려 있으면 팝업 호스트가 열지 않는다.
  - 플레이어 문맥은 조준 컨트롤러가 깨어날 때 만들어 든다. 소지 오브 컴포넌트는 깨어날 때 맵 매니저의 게임 규칙에서 용량과 기본 한도를 읽는다(맵 매니저가 먼저 깨어남).
  - 뷰모델(임시 모양): 회색 상자 손 위에서 구들이 천천히 돌며 떠 있다. '추출함'을 받으면 손을 뻗었다 돌아오고 새 구가 오브젝트 쪽에서 날아와 자리에 든다(0.6초). '추출 불가'를 받으면 손과 구가 짧게 흔들린다(추출 불가 효과, 임시). **뷰모델 레이어(`ViewModel`)만 그리는 오버레이 카메라**를 메인 카메라의 스택에 두어 벽에 붙어도 손이 벽에 묻히지 않는다(메인 카메라는 이 레이어를 그리지 않음).
- v1 `InteractionController`는 v1 필터(`FilterBlockBase`)에 기대므로 재사용하지 않는다. 0단계에서 v1과 함께 지우고, 같은 이름으로 새로 쓴다(코드 이름 Q510).

### 5.2 기물이 플레이어를 찾는 방법 [제안 Q500]

- **제안**: 기물은 전역 플레이어 Instance를 찾지 않는다. 조준 컨트롤러가 상호작용할 때 **플레이어 문맥**(`PlayerContext`: 소지 오브, 플레이어 위치, 이동 컴포넌트)을 넘긴다. 맵 매니저도 플레이어를 들고 있다(시작 지점으로 옮기기, 스냅샷, 문 계열의 막는 자리에 플레이어가 있는지 보기).
- 다른 방법: v1처럼 플레이어 정적 Instance. 어디서나 플레이어에 손댈 수 있어 의존이 보이지 않게 된다.

### 5.3 입력 (`InputManager`, v1 참고해 새로 씀)

- **Tab**: 누르는 순간을 읽는다(인벤토리 창 토글, 2차 Q462 ← 오브 흡수 채팅에서 토글만).
- **게임플레이 입력 잠금**: '잠근 쪽' 목록을 들고 하나라도 있으면 잠김이다. 팝업이 잠그고, 나중에 확인 창 등도 같은 방법으로 잠근다. 이동과 조준 컨트롤러가 이 잠금을 본다. 일시정지는 지금처럼 `Time.timeScale = 0`으로 멈춘다.
- **ESC**는 뒤로 가기 스택이 받는다(7.8).

## 6. 기물

### 6.1 공통 기반 (`FixtureBase`)과 인터페이스

```
FixtureBase (v2 기물 기반: 맵 안 id, 맵 매니저 등록, 강조, 상태 저장 기본 구현)
 ├ GateBase (문 계열 기반: 작동 대상 구현, 열림 상태)
 │   ├ Door (끼운 문)
 │   └ LaserWall (레이저 벽)
 ├ SubmittableObjectBase (작동기 계열 기반: 요구 값, 제출 세션, 든 오브)
 │   ├ ActuatorBase (작동기 기반: 작동 대상 1개, 연결색 표시)
 │   │   ├ SingleUseActuator (일회용 작동기)
 │   │   └ ReusableActuator (반복 작동기)
 │   └ Goal (목적지)
 ├ ColorSource (추출 오브젝트, 사물마다 프리팹)
 ├ FloorMoveBase (계단 계열 기반: 차지하는 칸, 코어 루프 뒤)
 │   ├ Stair (계단, 경사로는 그래픽 변형)
 │   ├ JumpPad (점프패드, 위층으로만)
 │   └ JumpDown (낙하구간, 아래층으로만)
 ├ SpawnPointBase (출발점 기반: 위치·시선)
 │   ├ StartPoint (시작 지점)
 │   └ Checkpoint (체크포인트, 코어 루프 뒤)
 └ ColorProcessorBase (오브 편집기 계열 기반)
     ├ ReusableProcessorBase (반복)
     │   ├ ColorMixer (합성기)
     │   └ ColorFilter (필터, 코어 루프 뒤)
     └ SingleUseProcessorBase (일회용, 코어 루프 뒤)
         ├ ColorCopier (복제기)
         └ ColorAmplifier (증폭기)
```

- 계열과 종류는 `Docs/v2 기물 분류.md`가 단일 출처다(코드 이름도 그 문서의 표). 문 계열 기반도 `FixtureBase` 아래라 맵 안 id·등록·상태 저장을 같이 쓴다. 끼운 문과 레이저 벽의 **모양**은 노드 시스템 쪽 컴포넌트(`DoorPiece`, `LaserSegment`, 11.4)가 맡는다.

| 인터페이스 | 뜻 | 구현하는 것 |
|---|---|---|
| 상호작용 (`IInteractable`) | 지금 상호작용할 수 있는가, 상호작용(플레이어 문맥) | 추출 오브젝트, 오브 편집기 계열, 작동기 계열 |
| 값 제공 (`IValueProvider`) | 보일 값이 있는가, 그 값(`TryGetDisplayValue`, 8단계) | 추출 오브젝트(추출 전), 작동기 계열(요구 값) |
| 상태 저장 (`ISnapshotable`) | 상태 내보내기·불러오기 | 상태가 있는 기물(기반에 '상태 없음' 기본 구현) |
| 작동 대상 (`IActuatorTarget`) | 연결색, 작동기 상태가 바뀜을 받음 | 문 계열(나중에 리프트 같은 기물도) |

- **상호작용과 값 제공을 나눈 이유**: 다 쓴 일회용 작동기는 상호작용은 안 되지만 값은 보인다(3차 Q478). 추출한 오브젝트는 둘 다 안 된다.
- **상호작용 강조**: 상호작용할 수 있는 동안 늘 약하게 강조한다(2차 Q193). 기반이 '상호작용할 수 있는가'가 바뀔 때 강조 겉모습 컴포넌트(`InteractHighlightView`)를 켜고 끈다. 강조 방법과 색은 미정이라 겉모습 컴포넌트 하나만 바꾸면 된다.
  - 4단계 임시 효과: 자체 발광을 숨 쉬듯 약하게 올렸다 내린다(흰색, 재질에 발광이 켜져 있어야 함). v1의 조준 아웃라인(`Outline.mat`, `InteractionHighlightOutline` 셰이더)은 쓰지 않아 '!!!!'를 붙였다(4단계 구상 채팅).
  - 발광 재질은 GI 플래그(Global Illumination)를 `RealtimeEmissive`로 둔다. URP는 이 플래그에 발광이 없으면 재질을 다시 불러올 때 `_EMISSION`을 지워 발광이 꺼진다(4단계 재질에서 생긴 문제를 5단계에서 고침).
- **맵 안 id**(`FixtureId`): 맵 안에서 1부터 늘어나는 정수(3차 Q487). 에디터가 발급하고(`FixtureIdAssigner`) 검사한다(12절).

### 6.2 추출 오브젝트 (`ColorSource`)

- 컴포넌트 하나를 사물마다 다른 프리팹(이름은 사물 이름, 예: 소화기)에 붙인다(코드 이름 Q508, 결정 로그 10절).
- 인스펙터: 값(`OrbValue`), 색을 칠할 렌더러 목록, 오브젝트 밝기(아트용, 값과 무관, 2차 Q454).
- 상호작용: 소지 오브에 더한다.
  - 성공: 추출됨으로 바꾸고, 흑백으로 칠하고, 강조를 끄고, '추출함'(위치·값)을 보낸다.
  - 가득 참: '추출 불가'(위치)를 보낸다.
- 값 제공: 추출 전만. 상태 저장: 추출됨 여부.
- 4단계 구현: 값의 색은 `MaterialPropertyBlock`으로 칠해 에디터에서도 보인다. 이벤트의 위치는 칠하는 첫 렌더러의 가운데다. 값 제공과 상태 저장은 받는 곳이 생길 때 더한다(8단계에서 값 제공을 더함, 상태 저장은 체크포인트 단계). 임시 프리팹은 회색 원기둥 `FireExtinguisher`(소화기)다.

### 6.3 합성기 (`ColorMixer`, 오브 편집기 계열)

- 상호작용: 합성 세션을 만들어 팝업 호스트에 연다.
- 세션이 합성할 때마다 알려 주면 '합성함'(위치·결과 값)을 보낸다. 세션은 순수 C#이라 EventBus를 모르므로, 월드 쪽인 합성기가 대신 보낸다.
- 오브 편집기 계열 기반(`ColorProcessorBase`)과 반복 기반(`ReusableProcessorBase`)은 지금은 얇게 둔다. 일회용 기반(`SingleUseProcessorBase`)은 복제기·증폭기를 만들 때 더하고, 다 쓴 뒤 팝업과 강조를 끄는 규칙은 일회용 작동기와 같다(결정 로그 2절, 3차 Q478).
- 5단계 구현: 기반 클래스는 아직 두지 않았다. 합성기 하나뿐이라 기반에 넣을 공통 부분이 없으므로 두 번째 오브 편집기(필터 등)를 만들 때 공통 부분을 보고 더한다(5단계 구상 채팅). '합성함'은 받는 곳(소리·연출)이 생기는 8단계에서 더했다(이벤트는 받는 곳이 있는 것만, 2차 Q267, 합성 세션의 알림을 합성기가 보냄). 임시 프리팹은 회색 상자 `ColorMixer`다.

### 6.4 작동기 계열 (`SubmittableObjectBase`)

- 인스펙터: 요구 값(`RequiredOrb`, 읽기 전용으로 내놓아 UI와 정답 검증 도구가 읽음, 2차 Q263).
- **판정**은 기반의 `TrySubmit` 한 곳이다(값이 정확히 같은가, 2차 Q147). 제출 세션은 이 판정을 받아 슬롯 이동·되돌리기를 다룬다.
- 기반이 하는 일: 팝업을 열 수 있는지 확인, 제출 세션 만들기, 팝업 열기, 닫힐 때 작동기 상태 갱신, 든 오브 겉모습(작동기 안에 든 모양, 2차 Q155) 갱신, 켜짐이 바뀌면 '작동기 바뀜'을 보내고 **응답**을 부름, 세션의 받아들임·거부마다 '제출 결과'를 보냄.
- **응답**(종류마다 재정의하는 곳):
  - 일회용 작동기(`SingleUseActuator`): 켜지면 다 씀(팝업이 다시 안 열리고 강조 꺼짐), 작동 대상에 알림.
  - 반복 작동기(`ReusableActuator`): 켜짐·꺼짐을 작동 대상에 알림.
  - 목적지(`Goal`): 켜지면 맵 매니저에 클리어를 요청.
- **연결**(작동기 1개 ↔ 작동 대상 1개, 3차 Q477 뒤 채팅): 문 계열이 연결된 작동기 목록을 든다(2차 Q270). 시작할 때 문 계열이 목록의 작동기마다 '네 대상은 나'라고 알려 준다. 작동기는 켜짐이 바뀌면 그 대상에 알리고, 대상의 연결색을 보인다. 연결색은 문 계열에서 고르므로 작동기는 따로 고르지 않는다(3차 Q492).
- 6단계 구현: 기반이 깨어날 때 작동기 상태를 만들고 요구 색을 칠한다(에디터에서도 보임). 일회용·반복 작동기는 종류만 다르다(다 씀·회수 규칙은 작동기 상태와 제출 세션이 정함). 임시 프리팹은 일회용 네모 받침, 반복 원기둥 받침이고(6단계 구상 채팅), 위쪽 띠가 요구 색, 아래쪽 띠가 연결색, 꼭대기 구가 든 오브다. '제출 결과'·'작동기 바뀜'은 받는 곳(소리)이 생기는 8단계에서 더한다(2차 Q267).
- 8단계 구현: 기반이 제출 세션의 알림을 받아 '제출 결과'를 보내고, 조준하면 요구 값을 보인다(다 쓴 뒤에도). '작동기 바뀜'은 작동기 기반만 보낸다(목적지는 '맵 클리어'로 알 수 있음).
- 7단계 구현: 목적지는 종류(목적지)와 응답(켜지면 맵 매니저의 클리어)만 다르다. 켜진 뒤에는 작동기 상태가 팝업을 막는다. 임시 프리팹은 작동기와 다른 넓고 낮은 원판이고, 위쪽 띠가 요구 색, 위의 구가 든 오브다(연결색 없음).

### 6.5 문 계열 (`GateBase`)

- 인스펙터: 연결된 작동기 목록, 연결색(연결색 목록의 번호).
- **열림 계산**: 작동기에서 알림을 받을 때마다 목록 전체를 다시 보고, **모두 켜져 있으면** 연다(AND만, 따로 세어 두는 값 없음).
- **열림 규칙**: 기본은 '작동기 상태를 그대로 따름'(3차 Q479). 저절로 닫히는 종류를 만들면 그 종류가 이 계산을 재정의한다(2차 Q469).
- **상태를 바꾸는 함수 하나**(2차 Q277): 콜라이더를 켜고 끄고, 겉모습 컴포넌트에 열림·닫힘을 알리고(문짝 미닫이, 레이저 오르내림), '문 계열 바뀜'을 보낸다. 루트 오브젝트와 스크립트는 늘 켜 둔다.
- **플레이어 위로 닫히지 않게**: 열린 문 계열의 막는 자리(닫혀 있을 때의 자리)에 플레이어가 있으면 연결된 작동기를 끄지 못하게 한다. 작동기는 그 회수를 거부하고(흔들림) 문 계열은 열린 채로 남는다(결정 로그 4절, 6단계 확인 채팅 ← 플레이어를 작동기 쪽으로 밀어냄, 방향은 Q503의 '가장 가까운 작동기 쪽(임시)'에서 6단계 구상 채팅의 '방금 꺼진 작동기 쪽'으로 바꿨다가 Play 확인에서 밀려나는 것이 문제라 없앰). 지금의 작동기는 회수로만 꺼지고 팝업 중에는 움직일 수 없으므로 이것으로 충분하다. 저절로 닫히는 종류를 만들면 그때 다시 본다.
- **상태 저장**: 따로 저장하지 않는다. 복원할 때 작동기를 먼저 불러온 뒤 문 계열이 열림을 다시 계산한다(10.1).
- **종류**
  - 끼운 문(`Door`, 모양은 `DoorPiece`): 노드 시스템이 일반 벽 구간에 끼워 만든다(2차 Q464). 겉모습(`DoorView`)은 가운데서 갈라지는 양쪽 미닫이(그림 0).
  - 레이저 벽(`LaserWall`, 모양은 `LaserSegment`): 노드 사이 구간 하나(2차 Q460). 겉모습(`LaserWallView`)은 반투명 면 + 천장의 발사 장치, 위로 올라가며 꺼진다(그림 1). 색은 미정이라 색 필드만 두고 값은 나중에 정한다.
- **연결색 목록**은 설정 애셋 하나다(`LinkColorConfig`, 10.2). 문 계열은 번호만 들고, 문 계열과 작동기의 색 표시 겉모습(`LinkColorView`)이 목록에서 색을 읽는다. 색 수와 색을 바꿀 때 애셋 하나만 고친다.
- 6단계 구현: 막는 콜라이더(상자) 목록(문짝 둘, 레이저 면)을 켜고 끈다. 깨어날 때 닫힌 막는 자리를 기억해 두고(문짝은 열리면 움직임), 그 자리와 플레이어 몸이 겹치는지로 '작동기를 꺼도 되는가'(작동 대상 인터페이스)를 답한다. 목록이 비면 늘 닫혀 있다. 문 계열도 기물이라 맵 안 id를 받는다(노드 시스템이 다시 만들어도 끼운 문 id로 남음). 겉모습은 문짝이 0.5초 동안 문짝 폭만큼 미끄러지고, 레이저 면은 0.4초 동안 아래에서부터 위로 줄어든다. 임시 연결색 표시는 문 위 띠와 레이저 발사 장치다(실행 중에만 칠함). '문 계열 바뀜'은 8단계에서 상태 함수에 더했다.

### 6.6 출발점 계열 (`SpawnPointBase`)

- 출발점 기반: 위치와 시선 방향.
- 시작 지점(`StartPoint`): 맵당 1개(에디터 검사). 맵 매니저가 시작할 때 플레이어를 여기로 옮긴다.
- 체크포인트(`Checkpoint`): 코어 루프 뒤에 같은 기반을 상속해 만든다(닿음 감지, 처음 닿을 때 맵 매니저에 스냅샷 요청).

### 6.7 계단 계열 (`FloorMoveBase`, 코어 루프 뒤)

- 계단(`Stair`, 위아래 모두, 경사로는 그래픽 변형), 점프패드(`JumpPad`, 위층으로만), 낙하구간(`JumpDown`, 아래층으로만). 코어 루프의 시험 맵은 한 층이라 코어 루프 뒤에 만든다.
- 계단 계열 기반이 **자기가 차지하는 칸**을 내놓고, 벽 빌더가 바닥·천장을 깔 때 그 칸을 뺀다(11.2). 층간 이동 칸을 알리는 컴포넌트를 따로 두지 않는다(제안의 `FloorOpening`을 합침, 결정 로그 10절).
- 점프패드와 낙하구간은 한 방향이다. 정답 검증은 이 연결을 방향이 있는 연결로 다룬다(결정 로그 7절).

### 6.8 새 기물을 더하는 방법

| 더할 것 | 하는 일 | 고치지 않아도 되는 것 |
|---|---|---|
| 새 작동기 종류 | 작동기 기반 상속, 응답 재정의, 프리팹 | 제출 팝업, 문 계열, 맵 매니저 |
| 새 문 계열 종류 | 문 계열 기반 상속(열림 규칙 재정의), 겉모습 컴포넌트, 노드 시스템 종류 | 작동기, 연결 |
| 작동기로 움직이는 다른 기물(리프트 등) | 작동 대상 구현 | 작동기 |
| 새 오브 편집기 종류 | 반복·일회용 기반 상속, 계산과 팝업(세션을 공통으로 묶을지는 두 번째 편집기 때, 4.4) | 조준, 맵 매니저, 소지 오브 |
| 새 설치형 기믹 | `FixtureBase` + 필요한 인터페이스(상호작용·값 제공·상태 저장) | 조준, 맵 매니저, 스냅샷 |
| 새 팝업 | 세션(코어 규칙) + 팝업 화면, 팝업 호스트에 화면 등록 | 입력 잠금, ESC, 커서 |
| 새 소리 | 소리 연결에 '이벤트 → 소리' 한 줄 | 소리를 내는 기물 |

## 7. 흐름

### 7.1 조준과 값 표시

1. 조준 컨트롤러가 화면 중앙으로 상호작용 거리만큼 레이캐스트한다. 가장 가까운 것 하나만 맞으므로 벽 너머는 안 된다. 큰 기물은 콜라이더 전체가 대상이라 표면 어디를 조준해도 된다(2차 Q214).
2. 맞은 콜라이더의 부모에서 v2 기물 기반을 찾는다.
3. (보일 값이 있는가, 값)이 바뀌었을 때만 '조준 대상 바뀜'을 보낸다. 추출 직후처럼 같은 대상의 값이 없어져도 여기서 잡힌다(8단계에서 대상은 비교에서 뺌, 5.1).
4. UI의 조준 값 표시가 조준점 오른쪽 위에 'R G B' 상자를 보이거나 숨긴다(2차 Q461).

### 7.2 추출

1. 좌클릭 → 조준 대상이 상호작용할 수 있으면 상호작용(플레이어 문맥).
2. 추출 오브젝트가 소지 오브에 더한다.
3. 성공: 추출됨, 흑백, 강조 끔, '추출함'. 소지 오브가 바뀌어 '소지 오브 바뀜' → 뷰모델에 구가 생기고, 인벤토리 창이 열려 있으면 다시 그린다. '추출함' → 소리, 뷰모델의 손 뻗기와 모이는 연출(0.5~1초, 보이기만, 2차 Q232).
4. 가득 참: '추출 불가' → 추출 불가 효과와 소리(글 알림 없음, 2차 Q229).
5. 다음 프레임에 조준 컨트롤러가 값이 없어진 것을 보고 값 표시를 숨긴다.

### 7.3 합성

1. 합성기 상호작용 → 합성 세션(소지 오브, 한도) → 팝업 호스트에 열기.
2. 팝업 호스트: 게임플레이 입력 잠금, 커서 보임, 뒤로 가기 스택에 '닫기'를 넣음, 합성 화면을 띄움.
3. 합성 화면: 소지 오브 목록을 그린다(모두 고를 수 있음). 오브를 누르면 고르기/취소 → 위 칸 'A + B → 결과'를 다시 그린다.
4. 결과를 누름 → 합성 → 소지 오브 바뀜(재료가 빠지고 결과가 끝에) → 합성기가 '합성함'을 보냄 → 팝업은 열린 채 목록을 다시 그린다(3차 Q480).
5. ESC나 닫기 버튼 → 팝업 호스트가 닫음 → 세션 닫기(선택 버림) → 입력 잠금 풂, 커서 숨김.

### 7.4 제출 (작동기·목적지)

1. 작동기 상호작용 → 팝업을 열 수 있으면 제출 세션 → 팝업 호스트에 열기(닫힐 때 할 일 포함).
2. 제출 화면: 왼쪽 위 요구 값(세 칸), 오른쪽 위 제출 슬롯, 아래 소지 오브 목록(그림 3·4).
3. 소지 오브를 누름 → 내기 → 받아들임: 오브가 슬롯으로 옮겨짐 / 거부: 그 오브가 제자리에서 흔들림. 작동기가 '제출 결과'를 보냄(소리).
4. 슬롯 오브를 누름 → 되돌리기·회수 → 소지 오브로 / 거부(소지 오브가 가득 참, 회수하면 닫힐 문 계열에 플레이어가 있음): 흔들림.
5. ESC나 닫기 버튼 → 팝업 호스트가 **먼저 다 닫고**(입력 잠금 풂) 그다음 '닫힐 때 할 일'을 부른다 → 세션 결과로 작동기 상태 갱신 → 켜짐이 바뀌었으면 '작동기 바뀜'과 응답.
   - 순서가 중요하다: 목적지의 클리어는 `GameManager.ClearMap()`을 부르는데, 이 함수는 Playing일 때만 동작한다. 팝업 정리가 먼저 끝나야 상태와 커서가 꼬이지 않는다.
6. 응답: 일회용 → 다 씀·강조 끔·대상에 알림 / 반복 → 대상에 알림 / 목적지 → 맵 매니저 클리어(7.6).

### 7.5 문 계열의 열림·닫힘

1. 작동기 → 작동 대상(문 계열)에 '작동기 바뀜'.
2. 문 계열: 목록 전체로 AND 계산 → 바뀌었으면 상태 함수: 콜라이더, 겉모습, '문 계열 바뀜'(소리).
3. 플레이어가 막는 자리에 있으면 그 전에 회수를 거부하므로 플레이어 위로 닫히지 않는다(6.5).
- 팝업을 닫는 순간 문이 움직이므로, 작동기 앞에서 문이 열리는 것을 볼 수 있다.

### 7.6 클리어

1. 목적지 응답 → 맵 매니저의 클리어.
2. 맵 매니저: 클리어 시간을 멈추고, '맵 클리어'(맵 id, 클리어 시간)를 보내고, `GameManager.ClearMap()`(상태 Cleared).
3. 임시 클리어 화면: '맵 클리어'를 받아 시간을 보이고, 시간을 멈추고 커서를 보인다(v1과 같은 방식). 버튼은 다시 하기(임시로 `SceneRestarter`)와 종료(`GameManager.QuitGame`). 메인 메뉴가 아직 없어 메인 메뉴 버튼은 메뉴 흐름을 만들 때 더하고(7단계 구상 채팅), '다음 맵'은 맵 목록 애셋을 만든 뒤 더한다.
4. 맵별 최고 기록 저장은 코어 루프 뒤: 전역 진행 쪽이 '맵 클리어'를 받아 저장한다(2차 Q468).
- 7단계 구현: 클리어 시간은 상태가 Playing인 동안만 흐르므로, Cleared가 되면 따로 멈추지 않아도 멈춘다. 클리어 화면(`MapClearScreen`)은 UIScene에 두고 일시정지 메뉴와 같은 모양(어두운 배경과 상자)이며, 시간은 '클리어 시간 mm:ss.ss'로 보인다. `timeScale`이 0이라 조준·이동·상호작용이 멈추고, 상태가 Cleared라 ESC로 일시정지가 열리지 않는다. 시험 씬의 목적지는 요구 값 (1,3,1)로 레이저 20 너머에 두었다(7단계 구상 채팅).

### 7.7 인벤토리 창 (`InventoryPopup`)

- Tab을 누르면 열고, 열려 있을 때 Tab이나 ESC를 누르면 닫는다(토글만, 2차 Q462 ← 오브 흡수 채팅에서 바뀜). 소지 오브 컴포넌트가 Tab을 받아 팝업 호스트에 연다. 그래서 다른 팝업처럼 게임플레이 입력을 잠그고(이동·시점 멈춤), 커서를 보이고, 뒤로 가기 스택에 들어간다. 다른 팝업이 열려 있으면 열리지 않는다(8.1).
- 소지 오브의 값 목록과 지금 채널 한도를 그린다. 코어 루프 8단계에서는 팝업 호스트에 소지 오브를 그대로 넘겨 열고(보기만 함), 흡수를 더할 때 흡수 세션을 넘기도록 바꾼다.
- 8단계 구현: 위에 '소지 오브', 가운데 슬롯 줄(들어온 순서의 오브 뒤에 남은 슬롯을 빈 원으로 보여 슬롯 수가 보임), 아래에 '채널 한도'와 세 칸. 창의 목적이 값 확인이라 오브 값은 마우스를 올리지 않아도 늘 보인다(합성·제출 화면은 마우스를 올릴 때). 열린 동안은 입력이 잠겨 소지 오브가 바뀌지 않으므로 열 때 한 번 그린다. 빈 슬롯 프리팹은 `Prefabs/UI/EmptyOrbSlot`.
- (코어 루프 뒤) **흡수 칸**: 오브를 끌어 흡수 칸 위에 두고 마우스를 누르고 있는 동안 흡수 칸 주변에 바뀔 한도를 보인다. 마우스를 떼면 흡수 세션이 흡수한다 → 소지 오브와 채널 한도가 바뀌고, 소지 오브 컴포넌트가 '오브 흡수함'과 '채널 한도 바뀜'을 보낸다. 되돌릴 수 없다.

### 7.8 ESC와 일시정지 — 뒤로 가기 스택 [제안 Q494]

- **제안**: 닫을 수 있는 화면(팝업, 나중에 확인 창·설정 패널)은 열 때 뒤로 가기 스택에 '닫기'를 넣고 닫을 때 뺀다. ESC는 스택 맨 위의 닫기를 부르고, **스택이 비어 있을 때만** 일시정지를 열고 닫는다(설계 문서 7.1, 2차 Q194). 일시정지 메뉴(`PauseMenu`, v1 `PauseMenuController`를 참고해 새로 씀)는 스택이 비었을 때만 ESC로 열고 닫는다. 코어 루프 동안은 '계속·처음부터·종료'만 두고, 설정 등은 메뉴 흐름에서 더한다(작업 순서 채팅).
- 다른 방법: 일시정지 메뉴가 '팝업이 열려 있는가'를 직접 확인한다. 닫을 화면이 늘 때마다 조건을 더해야 한다.
- 팝업은 상태(`GameState`)가 아니다. 팝업 중에도 클리어 시간은 흐르고(설계 문서 8.3), 일시정지는 팝업이 없을 때만 열린다.
- 5단계 구현: ESC는 일시정지 메뉴가 읽는다(`InputManager.ReadCancel`). 일시정지는 상태를 Paused로 바꾸고 `Time.timeScale = 0`으로 멈추고, 커서를 보이고, 스택에 '계속'을 넣는다. '처음부터'(`SceneRestarter`)는 시간을 되돌리고 지금 맵 씬을 이름으로 다시 불러온다(Build Settings에 있어야 함). '처음부터'·'종료'의 확인 창(2차 Q453)은 메뉴 흐름 때 더한다(5단계 구상 채팅). 에디터의 게임 뷰는 ESC를 누르면 스크립트와 상관없이 커서 잠금을 풀므로, 에디터에서 ESC로 닫으면 게임 뷰를 한 번 클릭해야 다시 잠긴다. 빌드에서는 생기지 않아 그대로 둔다(5단계 확인 채팅).

## 8. UI

### 8.1 팝업 호스트 (`PopupHost`, 인터페이스 `IPopupHost`, 접근점 `Popups`) [제안 Q493]

- **제안**: UIScene의 팝업 호스트가 켜질 때 **정적 접근점에 자기를 등록**한다. 인터페이스는 코어 규칙 쪽에 둔다(세션만 주고받으므로 순수 C#). 기물은 '팝업 열기(세션, 닫힐 때 할 일)'만 부르고 UI 클래스를 모른다. 등록된 호스트가 없으면 오류 로그로 바로 드러난다.
- 다른 방법: EventBus로 '팝업 열기 요청'을 보낸다. 닫힐 때 결과를 돌려받으려면 요청에 콜백을 실어야 하고, 받을 UI가 없으면 요청이 조용히 사라진다.
- 맡는 것: 한 번에 팝업 하나(열려 있으면 다른 열기는 무시), 세션 종류에 맞는 화면 고르기, 게임플레이 입력 잠금, 커서, 뒤로 가기 스택, 닫기 버튼, '팝업 열림·닫힘' 이벤트.
- 팝업 화면은 세션 종류마다 하나이고 호스트에 등록한다(6.8 '새 팝업').
- 5단계 구현: 팝업 화면의 기반은 `PopupView`(이 세션을 그리는가, 그리기, 숨기기)이고 호스트의 화면 목록에 넣는다. 열면 커서를 풀고 닫으면 다시 잠근다. 열린 채로 맵 씬을 다시 불러오면 스택과 잠금만 치운다. '팝업 열림·닫힘' 이벤트는 만들지 않았다: 팝업이 열리면 입력이 잠겨 조준 대상이 비므로 조준 값 표시가 저절로 숨는다(8단계 구상 채팅). 8단계에서 인벤토리 창을 Tab으로 닫으려고 `Popups.Close`를 더했다.

### 8.2 오브 칸 (`OrbCellView`, 공통 UI 부품)

- 색 원 + 마우스를 올리면 뜨는 값 상자 + 흔들림 + 굵은 테두리(고름)를 한 부품에 둔다. 합성 화면, 제출 화면, 인벤토리 창이 같이 쓴다. 인벤토리 창의 끌어다 놓기는 흡수를 만들 때 더한다.
- 'R G B' 값 상자도 부품 하나다(`OrbValueLabel`, 조준 값 표시, 요구 값, 마우스 올림이 같이 씀, 그림 2·3·5).
- 소지 오브 목록은 빈칸 없이 들어온 순서로 놓는다(2차 Q228, Q249).
- 5단계 구현: 테두리는 색 원 뒤의 검은 원이다(고르면 3 → 8픽셀). 원 그림은 내장 `Knob` 스프라이트(임시)이고, 값 상자는 칸 위에 뜨며 옆 칸에 가리지 않게 따로 그린다. 프리팹은 `Prefabs/UI/OrbCell`, '+'·'→' 글자는 `Prefabs/UI/PopupSymbol`. 흔들림은 제출 화면(6단계)에서 더한다. 값 상자를 늘 보이는 기능(`PinValue`)은 인벤토리 창을 위해 8단계에서 더했다.
- 6단계 구현: 흔들림은 칸 안의 모양 부분(`Visual`)만 좌우로 흔든다(칸 자체는 줄 배치가 움직임). 값 상자는 채널 글자 3개로 바꿔, 마우스 올림 상자는 칸 없이, 제출 화면의 요구 값은 칸을 나눠 같은 컴포넌트로 그린다.

### 8.3 합성 화면(`MixPopup`)과 제출 화면(`SubmitPopup`)

- 합성 화면(그림 2): 위 칸 'A + B → 결과', 아래 칸 소지 오브 목록, 닫기 버튼. 세션의 선택·미리보기를 그대로 그린다.
- 제출 화면(그림 3·4): 요구 값, 제출 슬롯, 소지 오브 목록, 닫기 버튼. 세션의 받아들임·거부로 오브를 옮기거나 흔든다.
- 두 화면 모두 판정하지 않는다. 판정과 상태는 세션에 있고 화면은 그리기만 한다.
- 5단계 구현(합성 화면): 고르기·취소·합성마다 두 줄을 다시 그린다. 위 칸의 오브를 눌러도 취소되고, 결과 오브를 누르면 합성한다.
- 6단계 구현(제출 화면): 소지 오브를 누르면 내고, 받아들이면 다시 그리고 거부면 그 칸만 흔든다. 슬롯 오브(빈 원 위의 칸)를 누르면 회수하고, 거부면 슬롯 칸이 흔들린다. 결과는 닫을 때 작동기가 적용한다.

### 8.4 HUD

- 조준점: 흰색 '+', 색이 바뀌지 않는다(2차 Q193). v1 `CrosshairController`의 색 바꾸기는 v2에서 쓰지 않는다.
- 조준 값 표시(`AimValueLabel`): '조준 대상 바뀜'을 받는다. 팝업이 열리면 숨긴다(입력이 잠겨 조준 대상이 비므로 따로 듣지 않음, 8단계). 8단계 구현: 값 상자는 오브 칸의 값 상자와 같은 모양이고 조준점에서 오른쪽 위로 24픽셀 떨어져 있다.
- 인벤토리 창(`InventoryPopup`): 팝업이다(7.7).
- 임시 클리어 화면(`MapClearScreen`): 7.6.

### 8.5 v1 UI

- v1 UI는 UIScene과 함께 모두 14절 0단계에서 지우고, UIScene은 v2 UI만으로 새로 만든다(작업 순서 채팅). 그래서 v1과 같이 있는 동안의 처리([제안 Q498]: 같은 UIScene의 v2 UI 루트, v1 전용 UI 숨김)는 필요 없어졌다(코드 이름 Q505).

- '처음부터'(씬 재로드로 할지는 미정, 2차 Q291), 체크포인트로, 이어하기, 낙사 안전망(2차 Q139).

## 11. 벽 노드 시스템

### 11.1 데이터

- **노드 그래프** 컴포넌트(`NodeGraph`, 맵마다 1개)가 노드 목록, 벽 목록, 다음 id를 든다. 항목 클래스는 코어 규칙의 노드 데이터(4.8)다.
- 노드: id, 정수 좌표 (x, y, z). y는 그 노드가 선 층의 바닥 높이(2차 Q321).
- 벽: id, 양 끝 노드 id, 종류(일반 벽 / 레이저 벽), 재질 번호(2차 Q354), 끼운 문(id, 위치 0.25 단위, 설정).
- 끼운 문에도 id가 있다. UGC 맵에서 작동기 연결을 id로 담기 때문이다(3차 Q487).
- 노드 그래프는 맵 씬에 **따로 둔 루트 오브젝트**다. 맵 기본 프리팹(`MapRoot`) 안에 두면 만든 벽이 전부 프리팹 오버라이드가 되기 때문이다. 노드 좌표는 노드 그래프 기준이다(3단계).

### 11.2 만들기 (벽 빌더 `NodeGraphBuilder`)

- **같은 빌더**를 에디터(유니티 에디터 맵, Undo 기록)와 런타임(UGC 맵)에서 쓴다(2차 Q458).
- 일반 벽 구간: 루트 오브젝트(데이터 id를 기억) 아래에 0.25 모듈 반복, 콜라이더 상자 하나(2차 Q330). 노드마다 기둥을 두고 남는 길이는 기둥이 가린다(2차 Q459).
- 끼운 문: 구간 안에서 문 자리만 모듈을 비우고 문 프리팹(문 계열)과 문 위 벽을 놓는다.
- 레이저 벽: 레이저 프리팹 하나를 구간 길이에 맞게 늘리고(2차 Q465), 천장 장치를 붙인다.
- 바닥·천장: 층마다 그 층의 노드를 감싸는 사각형 안에 1×1 타일을 깔고 층간 이동 칸은 뺀다(계단 계열 기반이 자기 칸을 알림, 6.7, 2차 Q473, Q475). 가장 위층에는 천장을 따로 만든다. 코어 루프의 시험 맵은 한 층이라 단순한 경우부터 만든다.
- 에디터 맵에서 만든 오브젝트는 static으로 표시한다(정적 배칭·라이트맵).
- 3단계 구현
  - 임시 회색 프리팹은 1×1×1 상자이고 빌더가 기준 치수로 늘린다. 9단계에서 숫자만 바꿔 걸어 볼 수 있다. 진짜 모양이 오면(월드/아트) 프리팹이 치수를 갖게 바꾼다.
  - 구간 끝에 남는 길이는 양 끝에 반씩 나눈다(한쪽 0.125 미만, 기둥 0.3이 가림).
  - 콜라이더: 문이 없는 구간은 노드에서 노드까지 상자 하나, 문이 있는 구간은 문 양옆 둘과 문 위 벽 하나. 기둥에도 콜라이더를 둔다(기둥이 벽보다 굵어 모서리가 튀어나옴).
  - 끼운 문은 문 프리팹의 루트(`DoorPiece`)를 벽 구간 루트의 자식으로 둔다(문짝 반쪽 둘, 닫힌 채). 레이저 벽은 레이저 프리팹의 루트(`LaserSegment`)를 구간 가운데에 두고 레이저 면만 늘린다.
  - 바닥·천장 판은 (x, 판 높이, z)의 집합으로 계산해 아래층 천장과 위층 바닥이 한 판이 되고, 넓이가 다른 층은 합쳐진다.
  - static 표시는 프리팹에 해 둔다(문짝·레이저는 움직이므로 뺌). 에디터에서 만들고 고치고 지우는 것은 Undo에 기록한다(`NodeBuildOps`).

### 11.3 다시 만들기 [제안 Q496]

- **제안**: 다시 만들 때 **데이터 id로 지금 오브젝트와 비교**한다.
  - 남은 id: 오브젝트를 지우지 않고 위치·길이와 안쪽 모듈만 다시 만든다.
  - 없어진 id: 지운다. 새 id: 만든다.
  - 그래서 끼운 문·레이저 벽의 인스펙터 값(연결된 작동기 목록, 연결색)과 다른 기물이 그 오브젝트를 가리키는 참조가 남는다. 미정 표의 '노드를 고쳐 다시 만들 때 인스펙터 값을 지키는 방법'(2차 Q458)을 이 방법으로 정한다.
  - 규칙: 손으로 넣는 값은 루트 오브젝트의 컴포넌트에 둔다. 루트 아래 '만든 부분'은 다시 만들 때 지워진다.
- 벽 종류가 바뀌면(일반 벽 ↔ 레이저 벽) 루트를 새로 만든다. 기둥·바닥·천장은 손으로 넣는 값이 없어 통째로 다시 만든다(3단계).
- 다른 방법: 에디터 맵도 UGC처럼 연결을 id로 들고 다시 만든 뒤 다시 잇는다. 인스펙터 직접 참조(2차 Q266)와 어긋난다.

### 11.4 상속 구조

```
NodeObjectBase (노드 시스템 기물 기반: 데이터 id, 만들기·다시 만들기)
 ├ WallSegment (일반 벽 구간: 모듈, 기둥, 콜라이더, 끼운 문 자리)
 ├ DoorPiece (끼운 문의 모양: 일반 벽 구간이 만드는 자식)
 └ LaserSegment (레이저 벽 구간의 모양)
```

- 노드 시스템 기물 기반은 **모양**을 맡고(2차 Q357), 문 계열 기반(6.5)은 **동작**을 맡는다. 끼운 문과 레이저 벽은 두 컴포넌트를 같은 오브젝트에 붙인다(`DoorPiece` + `Door`, `LaserSegment` + `LaserWall`). C#은 클래스 하나만 상속하므로 모양과 동작을 나눠야 둘 다 상속 구조를 쓸 수 있다.
- 이동 발판 같은 새 종류는 노드 쪽을 상속하고 필요한 동작 컴포넌트를 붙인다.

### 11.5 노드 편집 도구 (`NodeGraphWindow` + `NodeGraphSceneTool`, 첫 범위)

- 전용 에디터 창 + 씬 뷰 조작(2차 Q331, Q343).
- 첫 범위(시험 맵을 만들 만큼, 3차 Q490): 노드 찍기(정수 스냅)·고르기·끌어 옮기기·지우기, 두 노드 잇기·벽 지우기, 벽 종류 바꾸기, 문 끼우기(위치), 다시 만들기, Undo/Redo(2차 Q351), 같은 자리 노드 자동 합치기(2차 Q352).
- 나중: 재질 고르기 화면, 층 표시, 여러 개 고르기, 각도 스냅(필요하면, 2차 Q345).
- 3단계 구현
  - 편집 동작은 `NodeGraphEditing`이 창과 씬 뷰 도구에 함께 준다. 편집마다 데이터 변경 → 같은 자리 노드 합치기 → 다시 만들기를 Undo 하나로 묶는다.
  - 씬 뷰 도구(노드 그래프를 고르면 툴바에 나타남): 빈 곳 클릭은 노드 찍기(창에서 고른 층 높이), 노드·벽 클릭은 고르기, **Shift+클릭은 고른 노드에서 벽 잇기**(빈 곳이면 노드를 찍고 이어 연달아 그림, 3단계 구상 채팅), 끌기는 노드 옮기기(놓을 때 다시 만듦), Delete는 고른 노드(붙은 벽 포함)나 벽 지우기.
  - 창(메뉴 `ColorMaze/노드 편집`): 층 높이, 노드·벽 목록, 고른 노드의 위치, 고른 벽의 종류와 문 끼우기·위치(끼울 수 있는 범위만), 다시 만들기 버튼. 노드 그래프가 없으면 만들기 버튼을 보인다.

## 12. 에디터 검사 (`MapValidator`)

- 메뉴는 `ColorMaze/` 아래에 둔다(예: ColorMaze/맵 검사, ColorMaze/Play: 열린 맵에서 바로 시작, 코드 이름 Q511).
- 메뉴 하나로 지금 맵을 검사하고, 가벼운 검사는 씬을 저장할 때 자동으로 한다.
- 검사하는 것
  - 맵 안 id: 겹침, 빈 id(고침 버튼으로 다시 발급)
  - 시작 지점 1개, 목적지 1개
  - 요구 값이 목표 규칙에 맞는가, 추출 오브젝트 값이 규칙에 맞는가(4.2, 추출 오브젝트는 4단계에서 만듦)
  - 작동기 연결: 작동기 하나가 두 문 계열의 목록에 있으면 오류, 어느 목록에도 없으면 경고, 문 계열의 목록이 비어 있으면 경고(3차 Q477 뒤 채팅의 구현 메모)
  - 노드: 노드 그래프 1개, 같은 자리 노드, 없는 노드를 가리키는 벽, 높이가 다른 노드를 잇는 벽, 문을 끼울 수 없는 위치(3단계에서 만듦)
- 맵 안 id 발급: 기물을 놓거나 복제하면 에디터가 다음 번호를 준다. 첫 버전은 '검사 + 고침 버튼'으로 시작해도 된다. 2단계에서 메뉴 `ColorMaze/맵 검사`(맵 매니저 1개, 맵 안 id, 시작 지점 1개)와 `ColorMaze/맵 안 id 고치기`로 만들었고, 맵 씬을 저장할 때 맵 안 id를 자동으로 검사한다.
- 6단계에서 요구 값과 작동기 연결 검사를 더했다. 경고(어느 목록에도 없는 작동기, 빈 목록)도 문제 수에 센다.
- 7단계에서 목적지 1개 검사를 더했다. 맵 안 id 고치기는 고친 뒤 Undo 기록을 바로 마무리하고 씬 변경 표시를 직접 한다. 프리팹 인스턴스의 Undo 기록은 프레임 끝에 처리되어, 고친 프레임에 저장하면 저장 뒤 씬이 다시 '바뀜'이 되고(이 때문에 테스트 실행이 '씬 저장' 창에 막힘), 인스턴스 값만 바뀌면 씬 변경 표시가 붙지 않았다.
- 검사하지 않는 것: '같은 연결색을 서로 보이는 곳에 두지 않음'은 기계로 정하기 어려워 맵 설계 규칙으로 사람이 지킨다(3차 Q492).
